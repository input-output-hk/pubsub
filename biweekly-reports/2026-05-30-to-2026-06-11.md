# PubSub - Bi-Weekly Report: 30 May - 11 June 2026

## Executive Summary

This period turned the list-based architecture into running code. The Rust prototype advanced through four Spec Kit features in sequence — topic-subscription filtering, a signed message-envelope with mock crypto, an event-loop/state-machine refactor, and a node subscription registry — each landing behind path-filtered CI, with topic-registry work now started on top. The node is now effectively read-only with respect to the chain: subscriptions are derived from a registry rather than mutated locally, and a static configuration file stands in for on-chain state so the system can be driven and verified through injected event queues. In parallel, the node-lifecycle flows were published with sequence diagrams, and the peer-sampling research thread reopened as a structured protocol survey (Basalt vs Honeybee and the wider family), with formal Basalt analysis deliberately paused until the landscape study is complete. The main open architectural question is whether peer sampling runs per-topic or network-wide — deferred pending the survey, since getting it wrong risks late-stage rework.

## [Rust PubSub node prototype](https://github.com/input-output-hk/pubsub/issues/36)

The prototype moved from scaffold to a structured, testable node over four merged features. **Topic-subscription filtering** ([PR #45](https://github.com/input-output-hk/pubsub/pull/45), [`002-topic-subscription-filtering`](../pubsub-node/specs/002-topic-subscription-filtering/)) added per-topic delivery filtering on the in-memory substrate. **Message envelope + mock crypto** ([PR #47](https://github.com/input-output-hk/pubsub/pull/47), [`003-message-envelope-mock-crypto`](../pubsub-node/specs/003-message-envelope-mock-crypto/)) reshaped `Message` into a signed-envelope hierarchy, introduced a `PublisherId` newtype, renamed the routing wrapper to `RoutingFrame`, and added signature verification on the receive path against a mock signature scheme — so the crypto seam is in place without committing to a final scheme. **Event-loop refactor** ([PR #50](https://github.com/input-output-hk/pubsub/pull/50), [`004-node-event-loop`](../pubsub-node/specs/004-node-event-loop/)) split the node into a crate-internal pure core (`NodeState` + `apply`) driven by a single event queue, with the shell switched over behaviour-preserving — this is the state-machine direction agreed in the 2 June session, and it makes state derivation directly testable by feeding specific event queues in. [PR #49](https://github.com/input-output-hk/pubsub/pull/49) added the shared event-queue seam that let the 004 and 008 work proceed in parallel.

Next: continue layering connection logic and the remaining lifecycle flows onto the pure core; keep module interfaces fixed so a future peer-sampling protocol slots in without re-architecture.

## [Node subscription registry](https://github.com/input-output-hk/pubsub/issues/53)

The node's subscription model was inverted: instead of node-local `subscribe`/`unsubscribe` mutations, subscriptions are now **derived from a registry** ([PR #51](https://github.com/input-output-hk/pubsub/pull/51), [`008-node-registry`](../pubsub-node/specs/008-node-registry/), ADR [0013](../pubsub-node/docs/decisions/0013-subscription-list-is-authoritative-for-node-interests.md)). The registry read interface was unified to a node-keyed watch (push-based), the read/write traits split, and multi-node self-discovery plus registry invariants covered by tests. This makes the subscription-list entry authoritative for a node's own topic interests ([PR #52](https://github.com/input-output-hk/pubsub/pull/52)) and removes a class of local-state divergence — a node cannot disagree with the registry about what it is subscribed to. A static configuration file currently substitutes for the on-chain registry, keeping the node read-only with respect to the chain.

Next: feature [013 — topic registry](https://github.com/input-output-hk/pubsub/issues/54) is now in progress on top of this, extending the registry-derived model to authorised-publisher state per topic.

## [Node lifecycle flows formalised](https://github.com/input-output-hk/pubsub/issues/37)

The node-lifecycle procedures were published with sequence diagrams ([PR #44](https://github.com/input-output-hk/pubsub/pull/44), [`docs/node-lifecycle/`](../docs/node-lifecycle/)): joining, leaving, publishing, topic creation, changing topic subscriptions, IP discovery, endpoint change, catch-up, and gap recovery. The flows were co-specified with the implementation so research specs and the prototype stay coherent. An explicit limitation was documented for message omission/availability — the system cannot currently distinguish an intentionally omitted message from one dropped by the network, the gap concern raised in the 2 June session and deliberately deferred from the current implementation.

Next: feed the lifecycle flows into the prototype's event-loop core as connection and catch-up logic is built out; revisit the gap/ordering strategy once the relevant flows are specified ([logbook 2026-06-02](../logbook.md#2026-06-02--pubsub-working-session-state-machine-refactor-gap-validation-deferred)).

## [Peer-sampling protocol evaluation](https://github.com/input-output-hk/pubsub/issues/35)

Following the SecureCyclon verdict, the peer-sampling thread reopened as a structured protocol survey rather than a single-candidate study. Denis compared **Basalt** and **Honeybee**: Honeybee uses random walks for uniformity and Byzantine resistance — efficient with respect to network size but heavy on up-front computation — while Basalt's cost scales with a view-size requirement that itself grows with the target security level. The methodology agreed: categorise candidates into families (random walk vs verifiable brokers), shortlist with Sandro, and decide via a comparative trade-off table — with formal modelling held back until a candidate is chosen. Evaluation criteria: maximum uniformity, acceptable resampling speed, Sybil/Byzantine resistance, and — emphasised by Ezequiel — *analysability and design elegance*, since highly structured adversarial models (e.g. SecureCyclon) are harder to validate ([logbook 2026-06-11](../logbook.md#2026-06-11--brainstorm-peer-sampling-protocol-evaluation-state-machine-prototype-per-topic-vs-global-sampling)).

The open architectural question: **per-topic vs network-wide peer sampling**. Per-topic gossip could scale better and allow domain-specific optimisation, but risks selfish forwarding and structured biases that undermine the randomness peer sampling is meant to provide. Decision deferred pending the survey, since settling it late risks discovering a chosen protocol cannot meet production Byzantine-resistance requirements.

Next: Denis to prepare an initial protocol categorisation and shortlist for the Tuesday session (syncing with Sandro first); formal analysis of Basalt paused until the landscape study completes.

## [Identity anchoring and ID-grinding](https://github.com/input-output-hk/pubsub/issues/22)

The 4 June brainstorm refined the identity story. Key rotation and forward-secure signatures were discussed against the SecureCyclon misbehaviour-eviction path — a compromised key otherwise lets an attacker fabricate evidence of past misbehaviour — with the conclusion that standardising key derivation is not yet blocking and should wait until the gossiping protocols are more clearly defined. Text was refined to record that **ID grinding is orthogonal to identity anchoring**: anchoring an identity to a Cardano credential does not by itself close the position-grinding surface, which the per-epoch ring-position derivation (issue [#22](https://github.com/input-output-hk/pubsub/issues/22)) addresses separately ([logbook 2026-06-04](../logbook.md#2026-06-04--brainstorm-key-rotation-sequence-integrity-securecyclon-presentation-framing)).

Next: continue the ED25519-malleability and key-derivation discussion on GitHub; pick the most constrained scheme once the gossiping protocols settle.

## [Incentives and deposit-based defence](https://github.com/input-output-hk/pubsub/issues/11)

The incentive discussion sharpened around deposits as the primary adversarial defence. Deposit mechanisms were proposed against adversaries subscribing to all topics to gain influence or peer connections for free; Jesus offered load-based instance separation (grouping low-frequency topics) plus encryption for specific use cases as an alternative. The agreed framing: even an adversary subscribed to every topic is contained if deposit and penalty levels are set high enough to make misbehaviour costly — so the security analysis targets those levels rather than the topic count. Rate limiting and aggregating topics into channels were noted as future extensions, deferred until the prototype core is finalised.

Next: revisit rate limiting and topic-to-channel aggregation after the prototype core stabilises; fold deposit/penalty sizing into the incentive-model write-up.
