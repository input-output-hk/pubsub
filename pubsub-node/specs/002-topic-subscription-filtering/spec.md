# Feature Specification: Topics + Topic-Subscription Filtering

**Feature Branch**: `002-topic-subscription-filtering`

**Created**: 2026-05-29

**Status**: Draft

**Input**: User description: "Add topic-based subscription filtering to the pubsub node. After this feature, every `Message` carries a `topic` field (a `TopicId`, opaque newtype around `String`, validated the same way `PeerId` is), and every `Node` tracks an in-memory set of subscribed topics. When a message arrives at a Node from the network, the Node inspects the topic: if it is in the subscription set the message is kept and surfaced via the existing `received_messages()` snapshot; if not, the message is silently dropped and an info-level log line records the drop for the operator. The `InMemoryNetwork` is unchanged — it stays a dumb pipe that routes by `peer_id` and never inspects payload, mirroring the contract a real transport (TCP, later) will offer.

The Node's send / emission API is unchanged in shape. Whoever constructs a `Message` supplies its topic; subscription state and emission are fully decoupled, so a Node may emit on a topic it is not subscribed to (publish authority will be enforced by the registry in a later feature, not by the local subscription set). A Node does not see its own emitted messages in `received_messages()` unless a peer forwards them back (the snapshot is strictly inbound-from-the-network).

Subscriptions are dynamic. The Node exposes synchronous, in-memory mutators: `subscribe(topic) -> SubscribeOutcome` and `unsubscribe(topic) -> UnsubscribeOutcome`, where the outcome enums distinguish the state-changing case (`Added` / `Removed`) from the no-op case (`AlreadyPresent` / `NotSubscribed`). The Node performs no I/O during these calls — any registry validation, persistence, or external notification belongs in a future wrapper layer. The initial subscription set is loaded from the TOML config at Node construction via a new top-level `subscribed_topics = [\"T1\", \"T2\"]` field (plain string array, empty or absent is valid; each entry parsed through `TopicId::from_str` the same way peer ids are validated today).

No wildcard subscription in this feature — subscriptions are an enumerated set of `TopicId`s. A Node with an empty subscription set is a coherent state (the publisher-only case): it can emit, but every inbound message is dropped. No warning, no error — just the per-message info log. The \"subscribe to all known topics\" question is revisited once the registry feature defines a closed universe of topics.

Tests demonstrate: a subscribed Node receives messages tagged with its topics; a non-subscribed Node silently drops messages tagged with other topics; a multi-topic Node correctly accepts the subset it subscribes to and drops the rest; `subscribe` / `unsubscribe` are idempotent (re-subscribing returns `AlreadyPresent`, unsubscribing an unknown topic returns `NotSubscribed`); the existing 001 N-node graph integration tests are extended with topics so multi-node fan-out behavior still holds.

Out of scope: cryptographic verification of messages (003); connection-close on receiving an off-topic message as a misbehavior signal (deferred until 004+); a `Node`-internal \"publisher\" abstraction or per-topic publish authority (the registry feature); wildcard subscriptions; persistence of subscription state across restarts; per-topic policy configuration. Terminology: this feature implements **topic-based subscription filtering**, not topic-based routing — the network does not route by topic, the receiver filters by topic."

## Clarifications

### Session 2026-05-29

- Q: Should the `Node` expose a public getter for the current subscription set? → A: Yes — add a synchronous snapshot getter `subscriptions()` that returns the current subscription set as a stable owned value, mirroring 001's `received_messages()` snapshot pattern. Tests assert against it as a set (entry order unspecified). Encoded as FR-013.
- Q: Should `TopicId` validation impose any character-class restrictions beyond `PeerId`'s rules (non-empty, no internal NUL)? → A: No — match `PeerId` validation exactly. No additional restrictions on whitespace, control characters, punctuation, or length. Naming structure (namespacing, publisher-scoping) is deferred entirely to the registry feature. FR-002's "no character-class restrictions beyond non-empty/no-NUL" clause is normative.
- Q: Should `subscribe` / `unsubscribe` emit structured log entries, and at what level for the idempotent no-op cases? → A: Yes — info-level structured log entry for state-changing outcomes (`Added` / `Removed`); debug-level structured log entry for idempotent no-op outcomes (`AlreadyPresent` / `NotSubscribed`). Encoded as FR-014. Symmetric with FR-011's drop-log pattern; debug-level for no-ops keeps the info stream uncluttered while leaving a replay / retry trail accessible at `--log-level debug`.
- Q: What concurrency semantics does the spec normatively guarantee for the subscription set across receive-path inspection and mutation calls? → A: Linearizable. Receive-path filter checks (FR-004), mutators `subscribe` / `unsubscribe` (FR-006), and the snapshot getter `subscriptions()` (FR-013) behave as if executing in some global serial order; once a mutator returns on one task, any subsequent receive-path inspection on any task sees the post-call state. For the in-memory single-process scope of 002, the natural implementation is interior mutability via a single mutex (mirroring 001's `Arc<Mutex<…>>` pattern in `src/node.rs:27`). Encoded as FR-015. Linearizability matters less in a single-process setting where lock-serialization is the only trivial implementation; stating it normatively prevents future iterations (persistence, distribution) from weakening the contract without an explicit ADR.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Single-Topic Subscriber Filters Off-Topic Traffic (Priority: P1) 🎯 MVP

A developer instantiates two nodes A and B sharing an InMemory network. A subscribes to a single topic T1; B (or any peer) emits messages tagged with various topics. A's `received_messages()` snapshot ends up containing only messages whose topic is T1; all other inbound messages are silently dropped at A's receive boundary, with an operator-visible info-level log entry recording each drop.

**Why this priority**: This is the irreducible demonstration of the feature — a subscribed receiver accepts on-topic messages and rejects off-topic ones. Without it, no other behavior (multi-topic, dynamic mutation, TOML loading) has meaning.

**Independent Test**: Spawn two nodes A and B sharing an InMemory network. Configure A's subscription set to `{T1}`. Have B send `Ping(N, topic=T1)` and `Ping(M, topic=T2)` addressed to A. Observe A's `received_messages()` snapshot contains exactly one delivery whose message is `Ping(N, T1)` and no entry corresponding to the T2 message.

**Acceptance Scenarios**:

1. **Given** A subscribed to `{T1}` and B configured to address A, **When** B sends `Ping(N, T1)` to A, **Then** A's `received_messages()` snapshot contains exactly one delivery whose message is `Ping(N, T1)` attributed to B.
2. **Given** A subscribed to `{T1}`, **When** B sends `Ping(M, T2)` to A, **Then** A's `received_messages()` snapshot does NOT contain that delivery, and A's structured log stream contains a single info-level entry naming the dropped message's topic (`T2`) and the sender's logical peer id (B's id).
3. **Given** A subscribed to `{T1}` and A itself emitting `Ping(K, T1)` addressed to some peer (not back to A), **When** the emission completes, **Then** A's `received_messages()` snapshot does NOT contain its own emitted message — only inbound deliveries from peers count.

### User Story 2 — Multi-Topic Node in N-Node Graph (Priority: P2)

A developer configures a 4-node graph where each node subscribes to a different subset of topics. Peers emit messages tagged across the full topic universe. Each node's `received_messages()` snapshot contains exactly the messages whose topics overlap with its own subscription set, regardless of which peer originated them.

**Why this priority**: Generalizes the P1 filter from "single topic on a 2-node graph" to "multiple topics on an N-node graph" — confirming that the filtering rule composes correctly with 001's existing multi-node behavior. Lower priority than P1 because P1 already proves the core filter; P2 demonstrates that nothing else breaks.

**Independent Test**: Construct four nodes A, B, C, D sharing an InMemory network, with subscriptions `A={T1}`, `B={T1,T2}`, `C={T2,T3}`, `D={T3}`. Have a designated peer emit one Ping per topic addressed in turn to each node (12 emissions total: 3 topics × 4 recipients). For each node, verify its `received_messages()` snapshot contains exactly the emissions whose topic appears in its subscription set, and no others.

**Acceptance Scenarios**:

1. **Given** the 4-node configuration above, **When** any peer addresses `Ping(_, T1)` to each of A, B, C, D in turn, **Then** A and B receive the message (in their respective snapshots) and C and D drop it.
2. **Given** the same configuration, **When** emissions on T2 and T3 are interleaved across rounds, **Then** each node's snapshot accurately reflects its per-topic filter and arrival ordering within each node's snapshot is the order in which its receive path observed retained messages (no cross-topic re-ordering inside one node's snapshot).
3. **Given** the same configuration extended with at least 100 sequential emissions distributed across the three topics, **When** every emission has completed, **Then** every node's snapshot satisfies the equality `snapshot == intended_deliveries ∩ node_subscriptions` exactly (zero false-positives, zero false-negatives) — extending 001's SC-002 multi-node ordering guarantee to the topic-filtered case.

### User Story 3 — Dynamic Subscription Transitions Take Immediate Effect (Priority: P3)

A Node mutates its subscription set at runtime via `subscribe` / `unsubscribe`, and the change takes effect on the next inbound message its receive path observes. A topic not in the initial subscription set causes messages to be dropped; after `subscribe(T)` returns `Added`, subsequent inbound messages tagged `T` are retained in the snapshot; after `unsubscribe(T)` returns `Removed`, subsequent inbound messages tagged `T` are again dropped. The Node's `received_messages()` snapshot grows monotonically — entries recorded while the Node was subscribed to a topic are NOT retroactively removed when the Node later unsubscribes from that topic.

**Why this priority**: Exercises the runtime API surface that distinguishes this feature's dynamic subscription model from a hypothetical static-at-construction model. Without this story, the spec demonstrates filtering only for the subscription subset configured at construction — leaving the entire `subscribe` / `unsubscribe` integration behavior (interaction with the receive path, ordering across transitions) unverified. SC-005 covers idempotency at the unit-test level; US3 covers the integration-level transition behavior on the receive path. Lower than P2 because P1 and P2 together already establish the static filter rule; P3 demonstrates that *changing* what the filter accepts works end-to-end at the snapshot-observation level.

**Independent Test**: Spawn two nodes A and B sharing an InMemory network. Construct A with initial subscription set `{T2}`. Drive a sequence of (B-emits → A-mutates) steps and inspect A's snapshot between steps:

1. B emits `Ping(1, T1)` and `Ping(2, T2)` addressed to A → A's snapshot contains exactly `Ping(2, T2)` (T1 dropped + info-logged).
2. A calls `subscribe(T1)` → outcome is `Added`. B emits `Ping(3, T1)` → A's snapshot now contains `Ping(2, T2)` and `Ping(3, T1)`.
3. A calls `unsubscribe(T1)` → outcome is `Removed`. B emits `Ping(4, T1)` and `Ping(5, T2)` → A's snapshot contains `Ping(2, T2)`, `Ping(3, T1)`, and `Ping(5, T2)` only — Ping(4, T1) is dropped + info-logged, and the previously-retained Ping(3, T1) entry remains in the snapshot.
4. A calls `subscribe(T2)` (T2 already in the set) → outcome is `AlreadyPresent`, set unchanged. A calls `unsubscribe(T1)` (T1 already absent) → outcome is `NotSubscribed`, set unchanged.

**Acceptance Scenarios**:

1. **Given** A constructed with subscription set `{T2}` and B configured to address A, **When** B emits `Ping(1, T1)` then `Ping(2, T2)` to A, **Then** A's `received_messages()` snapshot contains exactly one delivery (`Ping(2, T2)`) and an info-level log entry records the T1 drop.
2. **Given** the state at the end of Scenario 1, **When** A calls `subscribe(T1)`, **Then** the call returns `SubscribeOutcome::Added`, A's subscription set is `{T1, T2}`, and A's snapshot is unchanged by the call itself (the mutator has no side effect on past receipts).
3. **Given** A's subscription set is `{T1, T2}` and the snapshot contains the deliveries from Scenarios 1–2, **When** B emits `Ping(3, T1)` to A, **Then** A's snapshot grows to contain `Ping(2, T2)` and `Ping(3, T1)` (the T1 message is now retained because A's subscription set at the moment of receipt contains T1).
4. **Given** A's subscription set is `{T1, T2}` and the snapshot from Scenario 3, **When** A calls `unsubscribe(T1)`, **Then** the call returns `UnsubscribeOutcome::Removed`, A's subscription set is `{T2}`, the snapshot is unchanged by the call itself (no retroactive removal of the previously-retained T1 entry).
5. **Given** A's subscription set is `{T2}` again (post-unsubscribe), **When** B emits `Ping(4, T1)` then `Ping(5, T2)` to A, **Then** A's snapshot grows to contain `Ping(5, T2)` (the T2 message is retained), the T1 message is dropped + info-logged, and the previously-retained `Ping(3, T1)` from Scenario 3 REMAINS in the snapshot.
6. **Given** A's subscription set is `{T2}` (T2 already present), **When** A calls `subscribe(T2)`, **Then** the call returns `SubscribeOutcome::AlreadyPresent`, the subscription set is unchanged, and no entry is appended to the snapshot as a side effect of the call.
7. **Given** A's subscription set is `{T2}` (T1 absent), **When** A calls `unsubscribe(T1)`, **Then** the call returns `UnsubscribeOutcome::NotSubscribed`, the subscription set is unchanged, and no entry is appended to the snapshot as a side effect of the call.

### User Story 4 — Subscriptions Loaded from TOML at Node Construction (Priority: P4)

An operator authors a peer-list TOML file extended with a top-level `subscribed_topics = ["T1", "T2"]` field and starts a node pointing at that file. The node's resolved subscription set matches the file. The TOML grammar continues to reject unknown top-level fields (per 001's strict-parsing convention).

**Why this priority**: The operator-facing configuration boundary. P1, P2, and P3 are testable via in-process constructors and direct API calls; P4 makes the subscription dimension configurable outside the test harness and is the bridge to operator-level use. Lowest priority among the four stories because the in-process trio already exercises filtering, multi-node composition, and runtime mutation — P4 adds the file-loading layer on top of behavior already proven by the lower-numbered stories.

**Independent Test**: Place a TOML file on disk containing both `[[peers]]` entries (per 001) and `subscribed_topics = ["governance/announcements", "defi/intents"]`. Start a node passing it the path to that file (plus `--self-id`). Query the resolved subscription set; verify it equals `{governance/announcements, defi/intents}`. Then emit a message tagged `governance/announcements` from a peer addressed to this node and observe it appears in the snapshot; emit one tagged `something-else` and observe it is dropped + info-logged.

**Acceptance Scenarios**:

1. **Given** a TOML containing `subscribed_topics = ["a", "b"]` alongside the usual `[[peers]]` entries, **When** the node is started with the path, **Then** the node's resolved subscription set is exactly `{a, b}` and inbound messages tagged `a` or `b` are retained while other tagged messages are dropped (per FR-004).
2. **Given** a TOML with no `subscribed_topics` field, **When** the node is started, **Then** the node's subscription set is empty; the node starts successfully without warning; every inbound message is silently dropped (each with an info-level log entry per FR-011).
3. **Given** a TOML with `subscribed_topics = []` (explicit empty array), **When** the node is started, **Then** behavior is identical to Scenario 2.
4. **Given** a TOML in which one entry of `subscribed_topics` violates `TopicId` rules (e.g., empty string, internal NUL byte), **When** the node is started, **Then** startup fails with a clear, actionable error naming the offending entry and the config path; the node does NOT start with a partial subscription set (analogous to 001's US3 AS-2 malformed-config path).
5. **Given** a TOML with an unknown top-level field (e.g., `bogus_field = 1`) alongside `subscribed_topics`, **When** the node is started, **Then** startup fails with a `ConfigError::Parse` analogue (preserving 001's `deny_unknown_fields` convention).

### Edge Cases

- **Empty subscription set**. A Node started with no `subscribed_topics` line or an explicit `subscribed_topics = []` is a coherent operating state (the publisher-only case): the Node constructs successfully, can still originate emissions (per FR-007 and FR-008), and silently drops every inbound message with an info log. No warning, no error.
- **Re-subscribing to a topic already in the set**. `subscribe(T)` when `T` is already in the subscription set returns `SubscribeOutcome::AlreadyPresent`; the subscription set is unchanged; no log entry is emitted by the Node itself (the caller's wrapper layer MAY log, but the Node API does not).
- **Unsubscribing from a topic not in the set**. `unsubscribe(T)` when `T` is not in the subscription set returns `UnsubscribeOutcome::NotSubscribed`; the subscription set is unchanged; no error.
- **Duplicate entries in `subscribed_topics`**. If the TOML lists the same topic id twice (e.g., `subscribed_topics = ["a", "a"]`), the resulting in-memory set contains it once (set semantics). The loader MAY issue an operator-facing warning, but the resulting Node state is well-defined.
- **A Node emits on a topic it is not subscribed to**. Emission succeeds; the emitter's own `received_messages()` does NOT contain its emission (per FR-009). Whether a peer forwards a copy back through the network is a function of the network graph, not this feature.
- **Same topic emitted from multiple peers concurrently**. The InMemoryNetwork's existing routing and ordering rules (per 001 FR-013) apply unchanged; the receiver's snapshot reflects whatever per-sender ordering the pipe produces. Topic filtering is applied independently per delivery as it traverses the receive boundary.
- **Inherits all 001 edge cases**. Sends to unregistered ids continue to be dropped + warn-logged per 001 FR-010; the empty-peer-set case remains valid; trust-on-arrival behavior is unchanged.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Every `Message` MUST carry a `topic` field of type `TopicId` as a first-class component of the message. Pre-002 messages (i.e., 001's bare `Ping(N)` shape without a topic) are no longer valid; all messages constructed after this feature lands MUST carry a topic. The `Message` type's public shape is extended accordingly.
- **FR-002**: `TopicId` MUST be an opaque newtype around a UTF-8 `String`, parallel in shape and validation to `PeerId`. The validation rules MUST match those that 001 applied to `PeerId` (non-empty, no internal NUL bytes; see 001's `ConfigError::InvalidPeer` precedent in `src/config.rs`), parsed via `FromStr`. No internal structure (no namespacing, no publisher-scoping, no character-class restrictions beyond non-empty/no-NUL) is enforced at this stage; richer structure is deferred to the registry feature.
- **FR-003**: Each `Node` MUST maintain an in-memory set of subscribed `TopicId`s. The set is initialized at Node construction from an already-parsed in-memory value passed to the constructor; file I/O is the CLI/loader's responsibility (matching the parse-at-the-edge layering established in 001 FR-012). The set is mutable for the Node's lifetime via the API in FR-006; persistence across Node restarts is out of scope.
- **FR-004**: When the Node's receive path observes an inbound message delivered by the network, the Node MUST inspect the message's topic. The subscription-set lookup MUST be evaluated against the Node's subscription set *at the moment the inbound message is observed by the receive path*; runtime mutations to the set via FR-006's API MUST take effect for any message whose receive-path observation occurs after the mutating call has completed (US3 covers the integration-level behavior). **If the topic ∈ subscription set**, the message MUST be retained and surfaced via the receiver's `received_messages()` snapshot exactly as 001 FR-006 specified. **If the topic ∉ subscription set**, the message MUST be silently dropped: it MUST NOT appear in `received_messages()`, MUST NOT trigger any error, and MUST NOT be observable through any other in-process snapshot, counter, event stream, or callable API. The drop MUST emit a single structured log entry at info level per FR-011 — the log is the only observable artifact of the drop.
- **FR-005**: The `InMemoryNetwork`'s behavior MUST NOT change in this feature. The pipe routes by `peer_id` (per 001 FR-010), never inspects message payload or topic. Topic-based filtering is strictly receive-side and lives in the Node, not in the network. This preserves the contract that future real transports (e.g., TCP in feature 009) inherit unchanged: the transport delivers bytes addressed by peer id, and the receiver applies any content-based filter.
- **FR-006**: The `Node` MUST expose a synchronous subscription-mutation API:
  - `subscribe(topic: TopicId) -> SubscribeOutcome` where `SubscribeOutcome ∈ { Added, AlreadyPresent }`. `Added` MUST be returned when the topic was not previously in the set and the call added it. `AlreadyPresent` MUST be returned when the topic was already in the set; the call is an idempotent no-op in that case.
  - `unsubscribe(topic: TopicId) -> UnsubscribeOutcome` where `UnsubscribeOutcome ∈ { Removed, NotSubscribed }`. Symmetric semantics: `Removed` when the call removed an entry, `NotSubscribed` when the topic was not in the set (idempotent no-op).
  Neither call MUST perform any I/O, registry lookup, persistence, or external notification. The Result-wrapping that real failure modes would warrant (e.g., registry validation, persistence I/O) is intentionally absent in this iteration because no failure modes exist yet at the Node API boundary; future iterations may wrap these outcomes in a `Result` when failure modes appear, and that wrapping will be its own ADR.
- **FR-007**: The `Node`'s send / emission public API MUST NOT change in shape compared to 001. The topic is supplied at `Message` construction time by whoever instantiates the message; the Node ferries already-constructed messages unchanged. No new "publish on topic T" method is introduced on the Node — the topic dimension lives on the message, not on the call.
- **FR-008**: Subscription state and emission MUST be fully decoupled. A Node MAY emit a message whose topic is NOT in its own subscription set; the emission MUST NOT be rejected or warned about by the Node API. Whether the message is accepted at the receiver is governed by the receiver's subscription set (FR-004), not by the emitter's. Publish authority is a future concern bound to the registry, not to local subscription state.
- **FR-009**: A Node MUST NOT see its own emitted messages in its own `received_messages()` snapshot solely by virtue of having emitted them. The snapshot is strictly inbound-from-the-network: only deliveries arriving through the receive path are recorded. If a peer happens to forward a Node's own message back through the network (legitimate fan-out, future feature) and that forwarded copy arrives at the Node's receive path, the forwarded delivery IS a valid receipt and MAY appear in the snapshot — but the original local emission alone does not. (See workstream-level note N-001 in `specs/IMPLEMENTATION_NOTES.md` for the trigger to revisit this.)
- **FR-010**: The peer-list TOML schema MUST grow a single new top-level field: `subscribed_topics`, of type "array of strings". Each string MUST be parsed via `TopicId::FromStr`; a parse failure MUST surface as a `ConfigError::InvalidTopic`-equivalent variant naming the offending entry and the config path (analogous to 001's `ConfigError::InvalidPeer`). The field MUST be optional: an absent `subscribed_topics` line or an explicit empty array (`subscribed_topics = []`) are both valid and MUST yield an empty in-memory subscription set without error or warning. The strict-unknown-field policy from 001 (`#[serde(deny_unknown_fields)]`) MUST continue to apply at the top level — adding `subscribed_topics` MUST NOT relax this contract for other fields.
- **FR-011**: The structured log entry emitted for an off-topic drop (FR-004) MUST be at info level and MUST include at minimum:
  - The dropped message's `topic` value.
  - The sender's logical peer id (the value returned by `PeerDescriptor::id()` for the originating peer, per 001 FR-006).
  - The receiving Node's own peer id (for multi-node test-harness disambiguation; matches the convention 001 FR-010 implicitly relies on for warn-drop entries).
  - A stable event marker (e.g., a fixed event name like `topic_drop`) that operators can grep for.
  The log entry MUST NOT cite any FR identifier or spec section in operator-facing text (per the documentation convention established for operator-facing strings). The entry is for operator observability only; it MUST NOT be surfaced through any in-process snapshot, counter, event stream, or other API consumable by tests. Acceptance scenarios assert on `received_messages()` only.
- **FR-012**: The `Node` public constructor (and any factory entry points) MUST accept the initial subscription set as an already-parsed in-memory value (e.g., a collection of `TopicId`s), NOT a filesystem path or a TOML fragment. Loading and TOML parsing for `subscribed_topics` MUST be performed by the CLI/loader layer that already handles peer-list TOML in 001 (`load_peer_list` and friends in `src/config.rs`), yielding parsed values before the Node is constructed. This keeps Node construction filesystem-free and isolates I/O failure modes from domain logic, extending 001 FR-012's layering rule. The binary's CLI flags MUST continue to expose the config-path flag from 001 unchanged; no new CLI flag is required by this feature (the `subscribed_topics` field rides inside the existing config file).
- **FR-013**: The `Node` MUST expose a public, synchronous getter `subscriptions()` that returns the current in-memory subscription set as a stable owned snapshot value (e.g., a `Vec<TopicId>` or equivalent owned collection). The snapshot semantics MUST mirror 001 FR-006's `received_messages()` contract: the returned value MUST be unaffected by subsequent `subscribe` / `unsubscribe` calls on the same Node, so assertions over the result do not race with concurrent mutations on the receive path. The ordering of entries in the returned value is unspecified — the underlying state is a set, and tests asserting against the result MUST treat it as a set, not a sequence. This getter is the canonical observability mechanism for the subscription set, analogous to `received_messages()` for inbound traffic and to 001's `Node::peers()` for the static peer list. Acceptance scenarios in US3 that read "A's subscription set is `{...}`" are satisfied by this getter; the `SubscribeOutcome` / `UnsubscribeOutcome` returns remain the canonical signal for *whether a mutation changed state*, while `subscriptions()` is the canonical signal for *what the state currently is*.
- **FR-014**: The `Node` MUST emit a structured log entry on every return from the subscription-mutation API (FR-006), with the level keyed to the outcome:
  - `subscribe(T) → SubscribeOutcome::Added` MUST emit one info-level structured log entry naming at least the topic, the Node's own peer id, and a stable event marker (e.g., `topic_subscribed`).
  - `unsubscribe(T) → UnsubscribeOutcome::Removed` MUST emit one info-level structured log entry naming at least the topic, the Node's own peer id, and a stable event marker (e.g., `topic_unsubscribed`).
  - `SubscribeOutcome::AlreadyPresent` / `UnsubscribeOutcome::NotSubscribed` (the idempotent no-op cases) MUST emit a debug-level structured log entry naming the topic, the Node's own peer id, and a stable event marker. Debug-level is invisible at the `info` default established by 001's CLI contract but available with `--log-level debug` for replay / retry tracing.
  All four entries MUST follow the operator-facing-string convention used by FR-011: no FR identifier or spec-section citations in the entry text. The log entries are for operator observability only; they MUST NOT be surfaced through any in-process snapshot, counter, event stream, or other API consumable by tests — tests assert on the `Outcome` return values and on `subscriptions()` (FR-013), never on log content.
- **FR-015**: Operations on a Node's subscription set — the receive-path filter check (FR-004), the subscription mutators `subscribe` / `unsubscribe` (FR-006), and the snapshot getter `subscriptions()` (FR-013) — MUST be linearizable. Equivalently: the subscription set behaves as if all operations execute in some global serial order consistent with each call's program order. Operational consequences:
  - Once `subscribe(T)` returns on one task, any subsequent receive-path inspection on any task MUST observe `T` in the set when evaluating the filter for messages whose receive-path observation begins after the `subscribe` call returned. Symmetric for `unsubscribe(T)`.
  - Two concurrent `subscribe(T)` calls from different tasks MUST observably linearize: exactly one returns `SubscribeOutcome::Added` and the other returns `SubscribeOutcome::AlreadyPresent`; neither sees a torn state. Symmetric for concurrent `unsubscribe(T)`.
  - `subscriptions()` MUST return a snapshot reflecting some specific point in the linearized order, including all mutations on the caller's task that completed before the `subscriptions()` call, and excluding any partial state.
  For the in-memory single-process scope of this iteration, the natural implementation is interior mutability via a single mutex around the subscription set (mirroring 001's `Arc<Mutex<Vec<ReceivedDelivery>>>` pattern in `src/node.rs:27` for the receive queue). The linearizability contract is the normative requirement; the specific primitive (`Mutex`, `RwLock`, lock-free structure, …) is a plan-level choice. The contract is stated normatively here so future iterations introducing persistent or distributed state cannot weaken it without an explicit ADR.

### Key Entities

- **Message**: A discrete unit of communication exchanged between Nodes. After this feature, every Message carries `(topic, payload)` where `topic: TopicId` and `payload` is one of the message variants (the only variant defined so far is `Ping(N)`, inherited from 001). The topic is a first-class field on the message, not embedded inside the payload.
- **TopicId**: An opaque newtype around a UTF-8 `String`, parallel in shape and validation to `PeerId`. Unique identifier for a topic within the system. No internal structure (namespacing, scoping) is enforced; only the basic validation rules that already apply to `PeerId` (non-empty, no internal NUL).
- **Subscription Set**: A per-Node in-memory set of `TopicId`s describing the topics whose messages the Node accepts on the receive path. Initialized from TOML at Node construction; mutable at runtime via the subscribe/unsubscribe API; observable via the `subscriptions()` snapshot getter (FR-013); not persisted across restarts.
- **SubscribeOutcome / UnsubscribeOutcome**: Two enums returned by the subscription-mutation API. Each has two variants distinguishing the state-changing case (`Added` / `Removed`) from the idempotent no-op case (`AlreadyPresent` / `NotSubscribed`). No failure variants in this iteration.
- **Config (extended)**: 001's TOML peer-list grows a top-level `subscribed_topics` field (optional, array of strings). Empty or absent yields an empty subscription set. Other 001-era fields (`[[peers]]`, etc.) are unchanged. `deny_unknown_fields` continues to apply.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A developer can stand up a two-node topic-filter demonstration (US1) — instantiate two Nodes sharing an InMemory network, configure one to subscribe to a single topic, emit one on-topic and one off-topic Ping at it, and verify exactly the on-topic delivery appears in its `received_messages()` snapshot — in under 30 seconds of local execution time (excluding build/compile time).
- **SC-002**: A developer can construct a 4-node graph with mixed subscriptions (US2) and verify, across at least 100 sequential emissions distributed across at least 3 topics, that every node's `received_messages()` snapshot contains exactly the messages whose topic appears in its subscription set and no others. Verification: zero false-positive deliveries (a message with topic T appearing in a node not subscribed to T) and zero false-negative drops (a message with topic T missing from a node subscribed to T) across the run. Extends 001 SC-002's multi-node ordering guarantee to the topic-filtered case.
- **SC-003**: Changing a node's subscription set requires either (a) editing the `subscribed_topics` field in its TOML and restarting the node, or (b) invoking the runtime `subscribe` / `unsubscribe` API on the live Node — never source-code changes. The running system MUST reflect the new subscription state on the next message it observes through its receive path (no rebuild, no redeploy, no Node re-instantiation beyond case (a)). Extends 001 SC-003 to the topic dimension.
- **SC-004**: A new contributor reading `specs/002-topic-subscription-filtering/spec.md` together with the directory's `quickstart.md` can reproduce the multi-topic 4-node demonstration within one hour, without consulting `plan.md`, `research.md`, `contracts/`, ADRs, or any document outside the feature directory. Amendments to this spec that affect contributor-facing behaviour (FRs governing the TOML schema, the subscribe/unsubscribe API surface, the test names referenced in `quickstart.md`, or the user stories' Independent Tests) MUST land alongside the corresponding `quickstart.md` updates in the same commit; reviewers SHOULD reject a spec amendment that leaves `quickstart.md` outdated. Extends 001 SC-004's spec-quickstart cohesion rule.
- **SC-005**: `subscribe` and `unsubscribe` are demonstrably idempotent on a single Node. Invoking `subscribe(T)` then `subscribe(T)` again MUST return `Added` then `AlreadyPresent`; the subscription set MUST be identical after the second call to its state after the first. Invoking `unsubscribe(T)` on a subscribed topic then `unsubscribe(T)` again MUST return `Removed` then `NotSubscribed`; the subscription set MUST be identical after the second call to its state after the first. Verified by direct unit tests on the Node API.
- **SC-006**: The off-topic drop log emission (FR-004 + FR-011) is operator-visible at default log-level configuration (the same default that surfaces 001 FR-010's warn-level drop events). Verified by running US1's off-topic emission with the default log level and observing the structured info-level entry in the process's log stream, carrying the dropped topic and sender's peer id.
- **SC-007**: Runtime subscription transitions are observable through the Node's receive path. After `subscribe(T)` returns `Added` on a Node, the next inbound message tagged with `T` that arrives at that Node MUST be retained in the snapshot rather than dropped. After `unsubscribe(T)` returns `Removed` on the same Node, the next inbound message tagged with `T` that arrives MUST be dropped + info-logged rather than retained. Idempotent calls (`subscribe` on a topic already in the set; `unsubscribe` on a topic not in the set) MUST NOT alter the receive path's behavior on subsequent messages. The `received_messages()` snapshot grows monotonically across transitions — entries recorded while a topic was subscribed MUST remain in the snapshot after the Node unsubscribes from that topic. Verified end-to-end via US3's acceptance scenarios.

## Assumptions

- **Topics carry no semantic structure at this stage.** Any string passing `TopicId::FromStr` is a valid topic id. Namespacing (`<publisher>/<topic>`), publisher-scoping, registry lookup, and per-topic policy are all deferred to later features — the registry feature (008) for namespacing/authorization; future ADRs for per-topic config knobs.
- **No wildcard subscription.** Subscriptions are an enumerated set of `TopicId`s. A Node that wants to "subscribe to everything" must enumerate each topic of interest. The wildcard question is revisited when the registry feature defines a closed universe of topics with operator-authorized membership.
- **No persistence.** Subscription state lives in memory for the Node's lifetime. Restarting the Node re-reads the TOML; `subscribe` / `unsubscribe` calls made during a previous run do not survive. Persistence is out of scope for this feature; an ADR governing how persistence integrates will accompany whichever future feature first needs it.
- **No registry, no publish authority.** There is no check at this stage that the emitter is authorized to publish on a topic, nor that the topic exists in a global registry. Emission is decoupled from authorization. The registry abstraction (feature 008) and the real on-chain registry feed (feature 012) introduce these checks; 002 does not.
- **No cryptographic verification.** Topics are unsigned and unauthenticated in this feature; a misbehaving peer could in principle claim any topic on its outbound messages. Authenticating the publisher-topic binding is the next feature's concern (003: message envelope + mock crypto).
- **No connection-close on misbehavior.** Receiving an off-topic message is silently dropped — it does not escalate to closing the sender's connection or otherwise penalising the peer. That escalation is a future direction noted in `specs/ROADMAP.md` for feature 004+; the receiver-side filter established here is the seam that future feature will hook into.
- **Inherits all 001 assumptions.** Trust assumption, liveness assumption, single-process scope, no failure handling, configuration trust, no cryptography (extended to this iteration as well). Topic filtering layers on top of 001's substrate; nothing in 001's contract is altered.
- **`InMemoryNetwork` stays a dumb pipe.** The substrate is untouched. Topic filtering is strictly a Node-side concern. This mirrors how a real TCP transport (introduced in feature 009) will behave: the transport delivers framed bytes addressed by peer id; the receiver decides whether each delivery is admissible.
- **Local emission is not local receipt.** A Node does not observe its own emissions through `received_messages()`. Workstream-level note N-001 in `specs/IMPLEMENTATION_NOTES.md` records the trigger to revisit this (introduction of an operator-facing admin/REST API). 002 does not introduce such an API.
- **Terminology lock.** This feature implements **topic-based subscription filtering**. The InMemoryNetwork does not perform topic-based routing; receiver-side filtering is the only mechanism that distinguishes accepted from rejected traffic by topic in this iteration. Spec, ADRs, code comments, and operator-facing strings should use this vocabulary consistently:
  - **Topic** = the identifier carried on a message (`TopicId`).
  - **Subscription** = a Node's declared interest in a set of topics.
  - **Subscribe / unsubscribe** = the state-changing operations on the subscription set.
  - **Topic-based filtering** = the receive-side drop-or-keep operation.
  - **Routing** = reserved for transport-layer concerns (who sends to whom), which 002 does not touch.
- **No new CLI flag.** The `subscribed_topics` field rides inside the existing peer-list TOML; the binary's existing `--config` (or equivalent) flag is sufficient. 001's `--self-id` and `--log-level` flags continue unchanged.
