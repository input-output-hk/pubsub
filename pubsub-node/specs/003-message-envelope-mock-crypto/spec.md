# Feature Specification: Message Envelope + Mock Crypto

**Feature Branch**: `003-message-envelope-mock-crypto`

**Created**: 2026-06-03

**Status**: Draft

**Input**: User description: "Feature 003 extends pubsub_node::Message to the staged-design-synthesis §2.3 envelope shape — (topic, publisher_id, parent_hash, sequence, timestamp, payload, signature) — and introduces Signer / Verifier traits with a mock impl pair. On the receive path the node verifies each inbound message's signature against the publisher key in the envelope; signature-valid messages flow into the existing 002 arrival log unchanged, signature-invalid ones are silently dropped with a structured tracing event (event = \"message_dropped\", cause = \"invalid_signature\", info level, with self_id / from / topic / publisher_id fields).

The crypto trait shape, the mock-crypto factory (MockCryptoScheme with seeded ChaCha20 RNG via rand + rand_chacha, asymmetric-shaped via _public suffix derivation), and the no-Signer-on-Node decision are recorded in ADR 0009. The canonical envelope encoding (hand-rolled length-prefixed via a single Message::signed_bytes seam; parent_hash: Option<MessageHash> at the API with MessageHash::ZERO sentinel in the encoding; Timestamp(u64) Unix epoch milliseconds; MessageHash([u8; 32]) over SHA-256 of the canonical bytes; CBOR-canonical swap deferred to feature 009 or first cross-language consumer) is recorded in IMPLEMENTATION_NOTES.md N-004.

Arrival-time validation is signature-only — chain-integrity (parent-hash linkage, sequence monotonicity), gap detection, equivocation reporting, and publisher-authorization checks are all deferred per N-003 until features 008 (mock registry) and 012 (real registry) land. The Constitution Principle II TDD trigger applies to signature authenticity only in this iteration, not to chain integrity.

Node-side: a new Arc<dyn Verifier> constructor parameter; no Signer field is added (signing is caller-side; Node::send keeps its current shape and takes an already-built Message). In the same commit as the new invalid_signature emitter lands, the 002 receive-task topic_drop emitter renames to event = \"message_dropped\" / cause = \"topic_not_subscribed\", applying the project's saved drop-event convention consistently.

References to read before specifying:
- pubsub-node/docs/decisions/0009-crypto-trait-shape.md (crypto + mock decisions, full sketch and rejected alternatives).
- pubsub-node/specs/IMPLEMENTATION_NOTES.md N-003 and N-004 (deferred-revisit ledger entries).
- pubsub/docs/staged-design-synthesis.md §2.3 (canonical envelope shape and the three protocol properties it enables).
- pubsub-node/specs/ROADMAP.md §2 feature 003 (originating roadmap entry, open questions, dependency on 002).
- pubsub-node/specs/001-minimal-node-scaffold/ and pubsub-node/specs/002-topic-subscription-filtering/ (inherited substrate: Network trait, NetworkHandle, async send/receive, PeerId, TopicId, subscription set, received_messages snapshot).
- Saved memory feedback_message_dropped_event_convention (drop-event shape — applies across features, will rename 002's emitter alongside the new 003 emitter)."

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Signature Verification on the Receive Path (Priority: P1) 🎯 MVP

A developer instantiates two nodes A and B sharing an InMemory network and a shared verifier. A publisher constructs a `Message` envelope with the §2.3 shape — topic, publisher_id (carrying the publisher's public key), parent_hash (None for the first message), sequence, timestamp, payload, and a signature produced by signing the message's canonical bytes with the matching private key. B sends the message to A. A's receive path verifies the signature using the publisher_id from the envelope; on success, the message appears in A's `received_messages()` snapshot. When the same scenario runs with the signature replaced by arbitrary bytes (or the payload tampered with after signing), A's receive path rejects the message: it does not appear in the snapshot, and A's structured log stream contains a single info-level `event = "message_dropped"` entry with `cause = "invalid_signature"`.

**Why this priority**: This is the irreducible demonstration of the feature — the envelope shape, the verifier on the receive path, the binary contrast between accept-on-valid-signature and drop-on-invalid-signature. Without it, the rest of the feature has no operational meaning.

**Independent Test**: Spawn two nodes A and B sharing an InMemory network, both constructed with `Arc::new(MockCryptoScheme::with_seed([0u8; 32]).verifier())`. Build a `KeyPair` via the same scheme's `generate_keypair`. Construct a signed `Message` whose `publisher_id` carries that KeyPair's public key and whose `signature` is the result of signing `message.signed_bytes()` with the matching `TestSigner`. Have B send the message to A. Verify A's `received_messages()` snapshot contains exactly that delivery. Then construct a second message identical to the first except for one altered byte in `payload` (without re-signing) and send it to A; verify it does not appear in A's snapshot and that a single info-level `event = "message_dropped"` / `cause = "invalid_signature"` log entry was emitted naming A's self_id, B's peer id, the envelope's topic, and the envelope's publisher_id.

**Acceptance Scenarios**:

1. **Given** node A subscribed to topic `T1`, A constructed with a `TestVerifier`, and a `KeyPair` produced by a `MockCryptoScheme`, **When** B sends to A a `Message` tagged `T1` whose `publisher_id` wraps the KeyPair's public key and whose `signature` is the `TestSigner`-produced signature over the message's `signed_bytes`, **Then** A's `received_messages()` snapshot contains exactly that delivery, attributed to B.
2. **Given** the same setup as Scenario 1, **When** B sends a second message identical to the first except that the `payload` bytes are altered after signing, **Then** A's snapshot does NOT contain the second delivery, AND A's structured log stream contains exactly one info-level entry with `event = "message_dropped"`, `cause = "invalid_signature"`, `self_id` equal to A's peer id, `from` equal to B's peer id, `topic` equal to `T1`, and `publisher_id` equal to the envelope's publisher_id.
3. **Given** the same setup, **When** B sends a third message whose `signature` is replaced with 32 zero bytes (a deliberately bogus signature), **Then** A's snapshot does NOT contain it and the same `message_dropped` / `invalid_signature` log entry is emitted.
4. **Given** the same setup, **When** B sends a fourth message whose `publisher_id` does not match the key used to sign the message (signed with KeyPair X but the envelope claims KeyPair Y's public key), **Then** A's snapshot does NOT contain it and the same drop event is emitted.

### User Story 2 — Multi-Publisher Verification (Priority: P2)

A developer constructs multiple distinct publisher keypairs and emits messages signed by different publishers in turn through a node A subscribed to the relevant topics. A's receive path uses each message's own `publisher_id` to select the verification key — there is no single "node-wide publisher key". Messages signed by their declared publisher land in the snapshot; messages whose declared publisher does not match the signing key are dropped + logged.

**Why this priority**: Generalizes P1's single-publisher demonstration to the multi-publisher case that the protocol is actually for. Confirms that the verifier is keyed off the envelope's `publisher_id` per message, not off any per-node configured key. Lower priority than P1 because P1 already proves the verifier works at all; P2 proves it works the way the protocol requires.

**Independent Test**: Build three keypairs `(P_alice, P_bob, P_carol)` from one `MockCryptoScheme`. Sign one message per publisher tagged with the same topic `T1`. Have a sending node B deliver all three to A (subscribed to `T1`, holding a `TestVerifier`). Verify A's snapshot contains all three deliveries, each with its correct `publisher_id`. Then alter one message's `publisher_id` to a different publisher's public key (without re-signing); verify only the two unaltered messages land in the snapshot, with one `message_dropped` / `invalid_signature` entry for the altered one.

**Acceptance Scenarios**:

1. **Given** three keypairs Alice / Bob / Carol from a single `MockCryptoScheme` and three messages — one signed by each respective publisher — tagged with topic `T1`, **When** B sends all three to A (subscribed to `T1`), **Then** A's snapshot contains all three deliveries in arrival order, each carrying the correct `publisher_id`.
2. **Given** the same three signed messages but with Alice's message's `publisher_id` swapped to Bob's public key (the signature still being Alice's over the original bytes), **When** B sends all three to A, **Then** A's snapshot contains only Bob's and Carol's deliveries; one info-level `message_dropped` / `invalid_signature` entry names Alice's-message-claiming-Bob's-id.
3. **Given** a sequence of at least 50 messages drawn from a pool of 5 distinct publishers, signed by each respective publisher, **When** B delivers them in some interleaved order, **Then** A's snapshot contains exactly the 50 messages and the receive ordering is preserved per FR-008.

### User Story 3 — Filter Composition with Topic Subscription (Priority: P3)

The 002 topic-subscription filter and the new signature filter compose on the receive path. A message reaches A's snapshot only if (a) A subscribes to the message's topic AND (b) the signature verifies. Both filters drop with the same `event = "message_dropped"` structured tracing event, distinguished by the `cause` field (`cause = "topic_not_subscribed"` for the 002 case, `cause = "invalid_signature"` for the 003 case). The 002-era `event = "topic_drop"` emission is replaced by the new convention in the same commit; no double-emission, no legacy event name.

**Why this priority**: Closes the integration gap with 002. Without this story, a future operator reading logs would see a mix of old (`topic_drop`) and new (`message_dropped`) events, and the convention wouldn't actually be uniform. Lower priority than P2 because the filter mechanics are already established in P1/P2; P3 verifies that they compose correctly and that the project-wide drop-event convention is applied consistently.

**Independent Test**: Construct A subscribed to `{T1}`, holding a `TestVerifier`. Build a `KeyPair` and a valid `TestSigner` for it. Send four messages from B to A:

1. Topic `T1`, signature valid → expected outcome: appears in A's snapshot; no drop event.
2. Topic `T1`, signature invalid → expected outcome: dropped; one `message_dropped` / `invalid_signature` event.
3. Topic `T2`, signature valid → expected outcome: dropped; one `message_dropped` / `topic_not_subscribed` event.
4. Topic `T2`, signature invalid → expected outcome: dropped; exactly one `message_dropped` event with one of the two causes (the implementation MAY check either filter first; tests assert "one drop event occurred", not which cause won).

**Acceptance Scenarios**:

1. **Given** A subscribed to `{T1}` with a `TestVerifier`, **When** B sends a valid-signature on-topic message, **Then** A's snapshot contains exactly that delivery; no `message_dropped` event is emitted.
2. **Given** the same setup, **When** B sends a valid-signature off-topic message (topic `T2`), **Then** A's snapshot does NOT contain it; exactly one info-level `event = "message_dropped"` / `cause = "topic_not_subscribed"` entry is emitted (with `self_id`, `from`, `topic`); no `cause = "invalid_signature"` entry is emitted.
3. **Given** the same setup, **When** B sends an invalid-signature on-topic message, **Then** A's snapshot does NOT contain it; exactly one info-level `event = "message_dropped"` / `cause = "invalid_signature"` entry is emitted; no `cause = "topic_not_subscribed"` entry is emitted.
4. **Given** the same setup, **When** B sends a message that is both off-topic and invalid-signature, **Then** A's snapshot does NOT contain it; exactly one info-level `event = "message_dropped"` entry is emitted with one of the two causes (test asserts on event count and event name; not on which cause).
5. **Given** any of the above drop scenarios, **When** the structured log stream is inspected, **Then** no log entry with `event = "topic_drop"` appears anywhere in the stream — the legacy event name from 002 has been replaced.

### User Story 4 — Reproducible Mock-Crypto Keypairs from a Seed (Priority: P4)

A developer testing signature-verification flows builds a `MockCryptoScheme` from a known 32-byte seed and generates a sequence of keypairs. The byte content of each keypair is fully determined by the seed and the position in the call sequence. Re-running the same test with the same seed produces byte-identical keypairs. Switching to `MockCryptoScheme::from_entropy()` produces non-deterministic keypairs suitable for tests that explicitly want randomness.

**Why this priority**: Tests that assert against specific signature bytes, specific public-key bytes, or the `_public` suffix property of the mock all depend on the keygen being reproducible from a seed. Without this property, those tests become non-deterministic. Lowest priority among the four stories because the other three already cover the externally-visible verify/drop behavior; US4 covers the test-infrastructure property that makes the lower stories reliably testable, plus the explicit escape valve for tests that want fresh randomness.

**Independent Test**: Build two `MockCryptoScheme` instances both via `with_seed([0u8; 32])`. Generate three keypairs from each. Verify the corresponding pairs are byte-identical (`scheme_1.kp1.public == scheme_2.kp1.public`, same for private; same for kp2 and kp3). Build a third scheme via `with_seed([1u8; 32])` and verify its first keypair differs from the first two schemes' first keypair. Build a fourth scheme via `from_entropy()` and verify (statistically — overwhelmingly likely) that its first keypair differs from any of the seeded schemes' first keypairs.

**Acceptance Scenarios**:

1. **Given** two `MockCryptoScheme` instances both constructed via `with_seed(s)` for the same 32-byte `s`, **When** each generates `N` keypairs via successive `generate_keypair()` calls, **Then** for every `i ∈ 0..N`, the two schemes' `i`-th keypairs are byte-identical (same `public.as_bytes()`, same `private.as_bytes()`).
2. **Given** two `MockCryptoScheme` instances constructed via `with_seed(s_1)` and `with_seed(s_2)` for `s_1 ≠ s_2`, **When** each generates its first keypair, **Then** the two keypairs are NOT byte-identical (the seed change propagates into key bytes).
3. **Given** any `MockCryptoScheme` instance, **When** a keypair is generated and inspected, **Then** `derive_public(&keypair.private)` equals `keypair.public` (the public key is derivable from the private by the mock's `_public`-suffix convention).
4. **Given** any keypair generated as above, **When** a `TestVerifier` verifies a `Signature` produced by `TestSigner::new(keypair.private)` over arbitrary bytes `m`, against `keypair.public`, **Then** the verifier returns `Ok(())`.
5. **Given** any keypair generated as above, **When** a `TestVerifier` is asked to verify a signature with `keypair.public` swapped for a `PublicKey` whose bytes do not end in the `_public` suffix, **Then** the verifier returns `Err(VerifyError::Invalid)`.

### Edge Cases

- **First message from a publisher**: a publisher's first message on a topic carries `parent_hash = None`. The signed bytes encode this as 32 zero bytes (`MessageHash::ZERO`). Signature verification proceeds normally; no chain-integrity check fires in 003 (deferred per N-003). Subsequent messages from the same publisher continue to carry `parent_hash = Some(hash_of_previous)` — but 003 stores those messages without inspecting whether the hash matches anything in the arrival log.
- **Empty payload**: a message whose `payload` carries an empty body (zero-length `Ping`, or a future variant with an empty body) is encodable: the length-prefix is zero followed by no bytes. The signature is computed over the canonical bytes including the zero length; verification proceeds normally.
- **`Timestamp` at epoch origin or far future**: `Timestamp::from_millis(0)` (epoch origin) and `Timestamp::from_millis(u64::MAX)` are both valid envelope values. The signature covers the timestamp; verification compares signatures bytes-for-bytes without interpreting the timestamp.
- **`publisher_id` carrying random non-derived bytes**: a `Message` constructed by a caller bypassing `MockCryptoScheme::generate_keypair` (e.g., test code that writes `PublicKey(vec![0u8; 8])` directly) yields a `PublicKey` whose bytes do not end in `_public`. The verifier's `strip_suffix` returns `None` and `verify` returns `Err(VerifyError::Invalid)`; the receive path drops the message with `cause = "invalid_signature"`. No panic, no error escalation — the drop path handles malformed public keys uniformly with signature mismatches.
- **Replay of an identical signed envelope**: a verifier-valid envelope sent twice (byte-identical, same signature) is accepted twice and appears twice in the receiver's snapshot. 003 does not deduplicate; replay detection is a future concern (the synthesis §2.3 sequence-number-and-hash-chain mechanics support it once chain integrity lands per N-003).
- **Concurrent inbound stream of mixed valid/invalid signatures**: the receive path verifies one message at a time; signature failures on one message do not affect the processing of other messages, and the drop event for an invalid message does not interrupt the arrival order of subsequent valid messages.
- **Self-addressing under signed envelopes**: per N-002, the 002-era self-addressing edge case (a Node emitting a message addressed to its own peer id) is operationally exotic and the receive path treats it as a normal inbound delivery. Under 003 the inbound delivery is additionally signature-verified; a Node that sends itself a signed message will see it appear in its own `received_messages()` if the signature verifies. The N-002 trigger to revisit semantics under connection-based transports (feature 004+) is unaffected by 003.
- **Inherited 002 edge cases**: empty subscription set, re-subscribing / unsubscribing idempotency, duplicate `subscribed_topics` entries in TOML, and the receiver-filter behavior under multi-peer concurrent traffic all carry forward from 002 unchanged. The `subscribed_topics` TOML field is unchanged in 003; no new TOML field is introduced.
- **Inherited 001 edge cases**: sends to unregistered ids continue to be dropped + warn-logged per 001 FR-010; the empty-peer-set case remains valid. 003 layers signature verification on top of 001's substrate; nothing in 001's contract is altered.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Every `Message` MUST carry the staged-design-synthesis §2.3 envelope shape as first-class fields: `topic: TopicId`, `publisher_id: PublisherId`, `parent_hash: Option<MessageHash>`, `sequence: u64`, `timestamp: Timestamp`, `payload: MessagePayload`, and `signature: Signature`. The 002-era `Message { topic, payload }` shape is extended in-place; pre-003 message-construction call sites MUST be updated alongside this feature.
- **FR-002**: `PublisherId` MUST be a newtype around `PublicKey`, distinct at the type level from `PeerId`. `PublisherId` represents the message originator (the entity whose private key produced the envelope's signature); `PeerId` continues to represent the network neighbor that forwarded the message. Even when both happen to wrap the same `PublicKey` byte representation under a future iteration, the compiler MUST distinguish them — accidental cross-role use MUST be a compile error.
- **FR-003**: `PublicKey`, `PrivateKey`, and `Signature` MUST be concrete byte-newtype structs living in `pubsub_node::crypto`. Their internal byte representation is opaque to the rest of the crate; concrete `Signer` / `Verifier` impls choose how to interpret the bytes. None of these types MUST be parameterised by an associated type or generic parameter at the crate's public API surface (per ADR 0009's rejection of the `CryptoScheme`-as-associated-types pattern). `MessageHash` MUST be a fixed-width 32-byte newtype (`MessageHash([u8; 32])`) and MUST expose a public `ZERO` constant for use as the absent-`parent_hash` sentinel in `signed_bytes` encoding. `Timestamp` MUST be a newtype around `u64` carrying Unix epoch milliseconds, with constructors `Timestamp::now()` (resolving the system clock) and `Timestamp::from_millis(u64)` (for caller-controlled values, typically in tests).
- **FR-004**: A public trait `Signer` MUST be defined in `pubsub_node::crypto` with the shape `fn public_key(&self) -> PublicKey` and `fn sign(&self, msg: &[u8]) -> Signature`. The trait MUST be `Send + Sync`. The trait MUST take no type parameters and MUST NOT define associated types. The `msg` argument MUST be `&[u8]` (raw bytes), so callers can pass the output of `Message::signed_bytes()` directly without coupling the trait to the `Message` shape. A future `Ed25519Signer` (feature 011) and the v1 `TestSigner` (this feature) MUST both implement the trait without changing its surface.
- **FR-005**: A public trait `Verifier` MUST be defined in `pubsub_node::crypto` with the shape `fn verify(&self, key: &PublicKey, msg: &[u8], sig: &Signature) -> Result<(), VerifyError>`. The trait MUST be `Send + Sync`. The trait MUST take no type parameters and MUST NOT define associated types. `VerifyError` MUST be a typed enum living in `pubsub_node::crypto`; its v1 variant set is `{ Invalid }` (representing "signature does not match key+msg"). The error MUST implement `std::error::Error`, `Debug`, and `Display` per the crate-wide typed-errors convention (ADR 0005 lineage).
- **FR-006**: A `pubsub_node::crypto::mock` module MUST contain a `MockCryptoScheme` factory struct, a `KeyPair { public: PublicKey, private: PrivateKey }` value type, and concrete `TestSigner` and `TestVerifier` impls. The module MUST be public at the crate boundary so tests and downstream test harnesses can use it; the rustdoc on the module MUST carry a prominent **"MOCK — not unforgeable"** warning paragraph stating that any caller with read access to a `PublicKey` produced by this scheme can forge a signature that the matching `TestVerifier` accepts, and that the mock exists only to differentiate correct/incorrect key+message bindings in tests, not to make any authenticity claim. Real authenticity arrives in feature 011 (`Ed25519Signer` / `Ed25519Verifier`).
- **FR-007**: `MockCryptoScheme` MUST expose `with_seed(seed: [u8; 32]) -> Self` (constructing the scheme with a deterministic ChaCha20 PRNG seeded by the caller-supplied bytes) and `from_entropy() -> Self` (constructing the scheme with a PRNG seeded from OS entropy). Both constructors MUST yield a scheme that holds an internal RNG state; subsequent keypair generation draws from this RNG. The PRNG implementation MUST be `rand_chacha::ChaCha20Rng`, chosen as the standard idiomatic seeded RNG for the Rust ecosystem; the `rand` and `rand_chacha` crates are introduced as new direct dependencies of the crate under this feature.
- **FR-008**: `MockCryptoScheme` MUST expose `generate_keypair(&mut self) -> KeyPair`. Each call MUST draw fresh randomness from the scheme's internal RNG, producing a `KeyPair` whose `private.as_bytes()` is a freshly-drawn 32-byte block and whose `public` is derived from the private by appending a fixed byte suffix (FR-009). Successive calls on the same scheme MUST yield independent key pairs (the RNG advances). Two schemes constructed with the same seed via `with_seed` MUST yield byte-identical keypair sequences across all `generate_keypair` calls.
- **FR-009**: The `TestSigner` / `TestVerifier` mock pair MUST implement the asymmetric-shaped construction described in ADR 0009: `derive_public(&PrivateKey) -> PublicKey` MUST produce a `PublicKey` whose bytes are the private key's bytes concatenated with a fixed suffix `PUBLIC_SUFFIX: &[u8] = b"_public"`. `TestSigner::sign(msg)` MUST produce `Signature(sha256(self.private.as_bytes() || msg))`. `TestVerifier::verify(public, msg, sig)` MUST attempt to strip `PUBLIC_SUFFIX` from `public.as_bytes()`; if the strip fails (the bytes do not end in the suffix), `verify` MUST return `Err(VerifyError::Invalid)`. If the strip succeeds, `verify` MUST recompute `sha256(stripped_bytes || msg)` and compare byte-for-byte against `sig.as_bytes()`; mismatch MUST yield `Err(VerifyError::Invalid)`; match MUST yield `Ok(())`. The `PUBLIC_SUFFIX` constant MUST be declared once and used by both `derive_public` and the verifier's `strip_suffix` so the two operations remain byte-symmetric by construction.
- **FR-010**: `Message::signed_bytes(&self) -> Vec<u8>` MUST be defined as the single canonical-encoding seam used by both signature production and signature verification. The byte layout is hand-rolled length-prefixed concatenation: a 1-byte `version_tag` (value `0x01` for v1), then `u32` big-endian length followed by UTF-8 bytes for `topic`, then `u32` big-endian length followed by raw bytes for `publisher_id`'s underlying `PublicKey`, then exactly 32 bytes of `parent_hash` content (the wrapped `MessageHash` bytes if `parent_hash` is `Some`, otherwise the all-zero `MessageHash::ZERO` sentinel), then `sequence.to_be_bytes()` (8 bytes), then `timestamp.as_millis().to_be_bytes()` (8 bytes), then `u32` big-endian length followed by raw bytes for the `payload`'s encoded form. The `payload` encoding for the 002-inherited `MessagePayload::Ping(u64)` MUST be a 1-byte variant tag (`0x00` for `Ping`) followed by the `u64.to_be_bytes()` of the ping value; future variants will append new tag values without altering the existing tags. The rustdoc on `Message::signed_bytes` MUST document this byte layout in full (field order, widths, endianness, the `MessageHash::ZERO` sentinel for absent `parent_hash`, the `version_tag` value and meaning, the `MessagePayload` variant tags). Treat the rustdoc as part of the protocol surface — changes to the layout require a rustdoc update in the same commit (per IMPLEMENTATION_NOTES.md N-004 guidance).
- **FR-011**: `MessageHash` MUST be defined as the SHA-256 of a message's `signed_bytes`. A free function or associated function `MessageHash::of(&Message) -> MessageHash` (or equivalent) MUST be available so that downstream callers (test harnesses building a chain of messages, future replication logic) can produce the hash that becomes the next message's `parent_hash`. The hash algorithm is SHA-256, provided by the `sha2` crate introduced as a new direct dependency under this feature. The hash output width is fixed at 32 bytes regardless of any future change to the canonical encoding.
- **FR-012**: The `Node` constructor MUST accept a new parameter `verifier: Arc<dyn Verifier>` and MUST store it on the Node for the duration of the Node's lifetime. The parameter is required (not optional): a Node MUST be constructed with a non-None verifier, since unsigned messages have no place in the 003 envelope shape. The `Node` MUST NOT add a `signer` field at this iteration. `Node::send` MUST keep its current shape from 002 — it takes an already-built `Message` argument; construction of the signed envelope (including running a `Signer` to produce the `Signature`) is the caller's responsibility (test harnesses today, a future publisher CLI later). Adding a `Signer` field on `Node`, along with the per-publisher chain-head tracking that would make a `Node::send(payload)` ergonomic API possible, is a deliberate non-goal for 003 per ADR 0009.
- **FR-013**: The `Node`'s receive task MUST perform a signature-verification step on every inbound `Message` observed via the network's receive path. Concretely: for each inbound message `m`, the receive task MUST compute `m.signed_bytes()` and call `self.verifier.verify(m.publisher_id.as_public_key(), &m.signed_bytes(), &m.signature)`. **If `verify` returns `Ok(())`**, the message MUST pass through to the existing 002 topic-filter step (FR-004 of 002); the existing logic — subscription-set membership check, snapshot append on hit, drop+log on miss — applies unchanged from 002 to the verified message. **If `verify` returns `Err(VerifyError::Invalid)`** (or any future variant), the message MUST be silently dropped: it MUST NOT appear in `received_messages()`, MUST NOT trigger any error return to any caller, and MUST NOT be observable through any other in-process snapshot, counter, event stream, or callable API. The drop MUST emit a single structured log entry per FR-014. The signature-verification step MUST occur **before** the topic-subscription filter on the receive path, so that signature failures are surfaced as `cause = "invalid_signature"` rather than masked by an off-topic drop when both filters would reject; tests in US3 rely on this ordering.
- **FR-014**: The structured log entry emitted for a signature-verification failure (FR-013's `Err` path) MUST be at info level and MUST include at minimum:
  - A stable event marker: `event = "message_dropped"`.
  - A stable cause discriminator: `cause = "invalid_signature"`.
  - The receiving Node's own peer id (`self_id`).
  - The forwarding peer's logical peer id (`from`).
  - The envelope's topic (`topic`).
  - The envelope's publisher id (`publisher_id`).
  The log entry MUST NOT cite any FR identifier or spec section in operator-facing text (per the project-wide operator-facing-string convention shared with 002 FR-011 and FR-014). The log entry is for operator observability only; it MUST NOT be surfaced through any in-process snapshot, counter, event stream, or other API consumable by tests — acceptance scenarios assert on `received_messages()` for absence and on log capture for presence (per 002's pattern of treating structured log emission as operator UX, not part of the test-anchored contract).
- **FR-015**: In the same commit that lands the FR-014 emitter, the 002-era topic-filter drop emission MUST be renamed: the previous `event = "topic_drop"` MUST become `event = "message_dropped"`, with the new field `cause = "topic_not_subscribed"` distinguishing the cause. All other fields of the 002 emission (`self_id`, `from`, `topic`) MUST remain unchanged. Any 002-era test that filters log capture on `event == "topic_drop"` MUST be updated in the same commit to filter on `event == "message_dropped"` AND `cause == "topic_not_subscribed"`. After this rename, no source file in the crate MUST emit an entry whose event marker is the legacy `"topic_drop"` value; the project-wide receive-path drop convention is `event = "message_dropped"` with a snake_case `cause` field (per the saved memory `feedback_message_dropped_event_convention`). Future drop reasons (post-N-003 chain inconsistencies, format errors, expired messages, etc.) will add new `cause` values rather than new event names.
- **FR-016**: Arrival-time validation in 003 MUST be **signature-only**. The receive path MUST NOT inspect `parent_hash` for chain-integrity correctness, MUST NOT compare `sequence` against any prior message's sequence, MUST NOT detect or report gap conditions (a message with `sequence = N+2` arriving when the publisher's last-seen sequence was `N`), MUST NOT detect or report equivocation (two valid-signature messages from the same publisher with the same `(parent_hash, sequence)` but different `payload`), and MUST NOT check the publisher's authorization against any registry. These observations MAY hold useful information for future features; 003 explicitly defers all of them per IMPLEMENTATION_NOTES.md N-003. The 003 spec's TDD trigger (Constitution Principle II) applies to signature authenticity only — chain-integrity tests do not appear in this iteration because the corresponding behavior does not appear in this iteration.
- **FR-017**: The TOML node-config schema MUST NOT change in 003. The 002-era top-level `subscribed_topics` field, the `[[peers]]` entries, and the strict-unknown-field policy all remain unchanged. Because signing is caller-side (FR-012) and the Node does not hold a `Signer`, no publisher key material is loaded from the TOML at this stage. The `Arc<dyn Verifier>` parameter to `Node::new` is constructed by the binary's `main.rs` and by test harnesses programmatically (typically via `MockCryptoScheme::with_seed(...).verifier()` for tests and a static `TestVerifier` for the binary at this prototype-stage iteration); no configuration knob exposes the choice of verifier in 003.
- **FR-018**: The crypto trait set (`Signer`, `Verifier`, `PublicKey`, `PrivateKey`, `Signature`, `VerifyError`) MUST be designed so that the future swap to real Ed25519 in feature 011 does not change any public API signature in `pubsub_node`. Concretely: the 011 work will add an `ed25519` submodule next to `mock` (with `Ed25519Signer`, `Ed25519Verifier`, and an `Ed25519CryptoScheme`), swap the binary's verifier construction from `MockCryptoScheme::*.verifier()` to `Ed25519CryptoScheme::*.verifier()`, and update the internal byte interpretation of `PublicKey` / `PrivateKey` / `Signature` to match Ed25519's curve representation. The trait surfaces, the `Node::new` parameter shape, the `Message::signed_bytes` rustdoc-documented byte layout, and the receive-task signature-verification call site MUST remain identical across the swap.
- **FR-019**: Concurrency semantics for the signature-verification step MUST be linearizable with respect to the rest of the receive path (extending 002 FR-015's linearizability contract to cover signature verification). Specifically, for any inbound message that passes signature verification, the post-verification topic-filter check (002 FR-004) and the post-filter snapshot append (002 FR-006) MUST observe a coherent point in the linearized order of subscription-set mutations (002 FR-006); a `subscribe(T)` returning `Added` on another task MUST be visible to the topic-filter check on any inbound message whose signature verification began after the `subscribe` call returned. The natural single-process implementation is for the verifier to be stateless (a unit struct or empty struct) so concurrent inbound messages can be verified in parallel without contention; the linearizability requirement is on the filter+snapshot path that follows verification, not on the verification step itself.
- **FR-020**: The receive-path signature-verification step MUST be confined to the Node's existing receive task (per 002's ADR 0006 receive-task model); 003 introduces no new async task and no new dispatch primitive. Concretely: the receive task's `while let Some(env) = rx.recv().await { ... }` loop in `src/node.rs` gains a verification step at the top of each iteration; the existing 002 topic-filter check and snapshot-append logic follow. The verifier call `self.verifier.verify(...)` is synchronous (returns `Result<(), VerifyError>` directly); it MUST NOT introduce an `await` point into the receive task. Future verifier impls (real Ed25519 in 011) that are CPU-heavy enough to warrant offloading MUST do so via their own internal mechanism (rayon, blocking-thread-pool) without changing the trait's synchronous signature.

### Key Entities

- **Message (extended)**: a discrete unit of communication exchanged between Nodes. After this feature, every Message carries `(topic, publisher_id, parent_hash, sequence, timestamp, payload, signature)` per the §2.3 envelope shape; the 002-era `(topic, payload)` shape is extended in-place.
- **PublisherId**: a newtype around `PublicKey` identifying the originating entity of a message. Distinct at the type level from `PeerId` (which identifies a network neighbor). At prototype scale the wrapped `PublicKey` bytes ARE the publisher's key material; the future on-chain registry (feature 008/012) will validate the publisher's authorization to publish on a given topic.
- **PublicKey / PrivateKey**: opaque byte-newtype types in `pubsub_node::crypto`. The internal byte representation is interpreted by concrete `Signer` / `Verifier` impls; the trait API itself does not interpret them. v1 mock impls use 32-byte private keys with a `_public`-suffix-appended derivation for the matching public key; future Ed25519 impls use 32-byte private and public keys.
- **Signature**: an opaque byte newtype. v1 mock impls store 32 bytes (the SHA-256 hash output of the signing input); future Ed25519 impls will store 64 bytes (the Ed25519 signature format). Verification compares signatures byte-for-byte against the recomputed expected value.
- **MessageHash**: a fixed-width 32-byte newtype (`MessageHash([u8; 32])`) over the SHA-256 of `Message::signed_bytes`. Used as the `parent_hash` field's content type. Exposes a `ZERO` constant for use as the sentinel in `signed_bytes` encoding when `parent_hash` is `None`.
- **Timestamp**: a newtype around `u64` carrying Unix epoch milliseconds. Advisory only — the receive-path verifier does not compare timestamps against any clock; the timestamp's only role is to be included in the canonical signing bytes so the publisher's signature commits to a publication time the publisher chose to assert.
- **VerifyError**: a typed enum in `pubsub_node::crypto`. v1 variant set: `{ Invalid }` (signature does not match key+msg). Future variants (e.g., `KeyFormatInvalid`, `AlgorithmMismatch`) are anticipated when multi-algorithm verifiers arrive; the spec's drop semantics treat all `Err` variants uniformly at the receive path under 003.
- **Signer trait**: the abstract signing capability. Mock impl is `TestSigner`; future impl is `Ed25519Signer` (feature 011).
- **Verifier trait**: the abstract verification capability. Mock impl is `TestVerifier`; future impl is `Ed25519Verifier` (feature 011). Stored on `Node` as `Arc<dyn Verifier>`.
- **MockCryptoScheme**: a factory struct in `pubsub_node::crypto::mock` that owns a seeded RNG (`rand_chacha::ChaCha20Rng`) and produces `KeyPair` values plus constructs `TestSigner` / `TestVerifier` instances. Reproducibility from a 32-byte seed is part of its public contract.
- **KeyPair**: a `{ public: PublicKey, private: PrivateKey }` struct returned by `MockCryptoScheme::generate_keypair`. Callers consume the `private` half when constructing a `TestSigner` and embed the `public` half in a message envelope's `PublisherId`.

## Assumptions

- **Mock crypto is not unforgeable.** The `TestVerifier` can derive a `PrivateKey` from any `PublicKey` produced by the mock (by stripping the `_public` suffix), so anyone with read access to the mock's module source can produce a forged signature that the verifier accepts. This is a deliberate property of a mock: it makes the trait surface look like real asymmetric crypto without imposing the implementation complexity. Real authenticity arrives in feature 011 (`Ed25519Signer` / `Ed25519Verifier`). The "NOT UNFORGEABLE" warning is loud in rustdoc at multiple locations (SC-006).
- **No publisher-key registry yet.** A node cannot validate that the `publisher_id` on a message is authorized to publish on the message's topic. The signature-only validation in 003 means a node will accept any valid-signature message regardless of whether the publisher key has any standing in the system. Authorization checks layered on top of signature verification are deferred to feature 008 (mock registry) and feature 012 (real on-chain registry) per IMPLEMENTATION_NOTES.md N-003.
- **No chain-integrity validation at the receive path.** Parent-hash linkage, sequence monotonicity, gap detection, and equivocation detection all require chain state (per-`(topic, publisher)` head tracking, or stateless queries over the arrival log) that has no consumer in 003. The envelope fields are *present* so future features can interpret them, but nothing in 003 reads them beyond `publisher_id` (consumed by the verifier). The deferred logic is recorded in N-003 with revisit triggers at features 008 and 012.
- **Signing happens caller-side.** `Node::send` continues to take an already-built, already-signed `Message`. Tests build envelopes by hand (or via a small test-support helper); a future publisher CLI (post-008) will assemble envelopes in its own process and hand them to `Node::send`. No `Signer` field on `Node` and no per-publisher chain-head tracking on `Node` in 003.
- **No replay detection.** A byte-identical signed envelope received twice is accepted twice. Replay detection would consume the same chain state as integrity validation and is similarly deferred.
- **No persistence.** The arrival log lives in memory for the Node's lifetime (per 002's contract); 003 does not change persistence semantics. A future persistence ADR will govern how stored signed messages, if any, are encoded on disk and how key material for `Ed25519Signer` is stored.
- **Canonical encoding is hand-rolled, version-tagged, and swap-ready.** The `Message::signed_bytes` body is hand-rolled length-prefixed concatenation with a leading `version_tag` byte. The swap to CBOR canonical (RFC 8949 §4.2.2) is deferred to feature 009 (TCP transport) or first cross-language consumer per IMPLEMENTATION_NOTES.md N-004. The swap is a single-seam edit: the call sites for `signed_bytes` do not change.
- **Hash function is SHA-256.** `MessageHash` is SHA-256 of `signed_bytes`. The choice of hash function is not parameterised at this iteration; if a future feature needs blake3 or sha3 it adds a new internal seam, not a public type parameter on `MessageHash`.
- **PRNG is `rand_chacha::ChaCha20Rng`.** The mock keypair generation uses ChaCha20 seeded from a 32-byte seed (or OS entropy via `from_entropy`). Both `rand` and `rand_chacha` are introduced as new direct dependencies under this feature; both are widely-used standard Rust crates per the Constitution's justified-dependencies guidance.
- **`sha2` crate is introduced.** SHA-256 is provided by the `sha2` crate (RustCrypto family), introduced as a new direct dependency under this feature. The crate is vetted and ubiquitous; the alternative of rolling a SHA-256 implementation by hand is explicitly rejected.
- **Inherits all 001 + 002 assumptions.** Trust assumption, liveness assumption, single-process scope, configuration trust, no failure handling, InMemoryNetwork as a dumb pipe, parse-at-the-edge layering, etc. all carry forward. 003 layers signature verification on top of 001's substrate and 002's topic filter; nothing in either prior contract is altered except the explicit 002 `topic_drop` rename per FR-015.
- **No new CLI flag.** The `Arc<dyn Verifier>` parameter is constructed programmatically in `main.rs` (and in test harnesses); 003 does not introduce a `--verifier` flag or any operator-facing configuration knob for choosing the verifier impl. When real Ed25519 lands in 011, the choice between mock and real verifier may surface as a config-time concern; in 003 the binary unconditionally uses the mock verifier at the prototype-stage iteration.
- **Drop-event convention applies workstream-wide.** The `event = "message_dropped"` + `cause` field shape established by FR-014 and the 002 rename in FR-015 is recorded as a project-wide convention in saved memory (`feedback_message_dropped_event_convention.md`). Any future receive-path drop reason (post-N-003 chain inconsistencies, future format errors, etc.) MUST add a new snake_case `cause` value rather than a new event name.
