# Feature Specification: Message Envelope + Mock Crypto

**Feature Branch**: `003-message-envelope-mock-crypto`

**Created**: 2026-06-03

**Status**: Draft

**Input**: User description: "Feature 003 extends pubsub_node::Message to the staged-design-synthesis §2.3 envelope shape — (topic, publisher_id, parent_hash, sequence, timestamp, payload, signature) — and introduces Signer / Verifier traits with a mock impl pair. On the receive path the node verifies each inbound message's signature against the publisher key in the envelope; signature-valid messages flow into the existing 002 arrival log unchanged, signature-invalid ones are silently dropped with a structured tracing event (event = \"message_dropped\", cause = \"invalid_signature\", info level, with self_id / from / topic / publisher_id fields).

The crypto trait shape, the mock-crypto factory (MockCryptoScheme with seeded ChaCha20 RNG via rand + rand_chacha, asymmetric-shaped via _public suffix derivation), and the no-Signer-on-Node decision are recorded in ADR 0009. The canonical envelope encoding (hand-rolled length-prefixed via a single Message::signed_bytes seam; parent_hash: Option<MessageHash> at the API with MessageHash::ZERO sentinel in the encoding; Timestamp(u64) Unix epoch milliseconds; MessageHash([u8; 32]) over SHA-256 of the canonical bytes; CBOR-canonical swap deferred to feature 009 or first cross-language consumer) is recorded in IMPLEMENTATION_NOTES.md N-004.

Arrival-time validation is signature-only — chain-integrity (parent-hash linkage, sequence monotonicity), gap detection, equivocation reporting, and publisher-authorization checks are all deferred per N-003 until features 008 (mock registry) and 012 (real registry) land. The Constitution Principle II TDD trigger applies to signature authenticity only in this iteration, not to chain integrity.

Node-side: a new Arc<dyn Verifier> constructor parameter; no Signer field is added (signing is caller-side; Node::send keeps its current shape and takes an already-built Message). In the same commit as the new invalid_signature emitter lands, the 002 receive-task topic_drop emitter renames to event = \"message_dropped\" / cause = \"topic_not_subscribed\", applying the project's saved drop-event convention consistently.

References to read before specifying:
- pubsub-node/docs/decisions/0009-crypto-trait-shape.md (crypto + mock decisions, full sketch and rejected alternatives).
- pubsub-node/specs/IMPLEMENTATION_NOTES.md N-003 and N-004 (deferred-revisit ledger entries).
- pubsub/docs/staged-design-synthesis.md §2.3 (canonical envelope shape and the three protocol properties it enables).
- pubsub-node/specs/ROADMAP.md §2 feature 003 (originating roadmap entry, open questions, dependency on 002).
- pubsub-node/specs/001-minimal-node-scaffold/ and pubsub-node/specs/002-topic-subscription-filtering/ (inherited substrate: Network trait, NetworkHandle, async send/receive, PeerId, TopicId, subscription set, received_messages snapshot).
- Saved memory feedback_message_dropped_event_convention (drop-event shape — applies across features, will rename 002's emitter alongside the new 003 emitter)."

## Clarifications

### Session 2026-06-03

- Q: When an inbound `Message` reaches the receive task and is hashed for signature verification, should the encoding include a leading 1-byte `version_tag` (so future encoding migrations are observable at the byte level)? → A: No — remove the version_tag entirely from FR-010's `signed_bytes` layout. In 003 the in-memory network passes `Message` Rust objects directly (no serialization), and the same code base both signs and verifies; an envelope-level version distinguisher would only ever differentiate two different builds of `TestSigner` / `TestVerifier`, which is a test-only artefact. When the encoding swaps to CBOR canonical at feature 009 per N-004, version identification rides on the CBOR scheme's own conventions rather than on a hand-rolled tag byte. FR-010 and the relevant Assumptions bullet are updated accordingly; N-004 in `specs/IMPLEMENTATION_NOTES.md` is updated to match (the encoding sketch and revisit-trigger no longer reference a version_tag).
- Q: Which standard Rust traits should `PublisherId` derive in 003? → A: Derive `Clone`, `Debug`, `Eq`, `PartialEq`, and `Hash`, matching the 001 / 002 convention for `PeerId` and `TopicId`. Future features that key on `PublisherId` — per-publisher chain heads after the N-003 deferral lifts, publisher-authorization lookups in feature 008, per-publisher counters / caches — need `Eq + Hash` to use the type as a `HashMap` key; deferring the derives would force a spec amendment when those features land. FR-002 is updated with a normative sentence specifying the derive set.
- Q: Which standard Rust traits should the sibling newtypes `PublicKey`, `PrivateKey`, and `Signature` derive in 003? → A: Split the convention along secret-vs-public lines, matching real Rust crypto crates (`ed25519_dalek` family). `PublicKey` derives `Clone, Debug, Eq, PartialEq, Hash` (a natural map key in future registries). `Signature` derives `Clone, Debug, Eq, PartialEq` only (no `Hash` — signatures are not natural map keys; replay/equivocation tracking should key on message-hash or `(publisher_id, parent_hash)` instead). `PrivateKey` derives `Clone, Eq, PartialEq` (no `Hash`, no derived `Debug`) and additionally carries a hand-written `Debug` impl that redacts the byte content, so panics and test-failure messages remain legible without leaking secret bytes. This carries the discipline forward to feature 011's Ed25519 swap (which will add `Zeroize` and constant-time comparison on `PrivateKey`). FR-003 is updated with normative bullets specifying each type's derive set, plus the redacting `Debug` requirement for `PrivateKey`.
- Q: What `Display` format do `PublicKey`, `PublisherId`, `Signature`, and `MessageHash` use for operator-facing log fields? → A: Full lowercase hex of the underlying bytes. `PublicKey` of bytes `[0x70, 0x75]` renders as `"7075"`; `Signature` and `MessageHash` follow the same convention; `PublisherId`'s `Display` delegates to its inner `PublicKey`. Matches what `ed25519_dalek` and other real Rust crypto crates use; carries forward unchanged when Ed25519's fixed-length 32-byte keys arrive in feature 011; operators can copy the hex into other tools without translation. `PrivateKey` does NOT implement `Display` (the redacting `Debug` is its only stringifying surface). FR-003 gains a Display-format bullet specifying these rules.
- Convention reminder (raised during Q4): **tests MUST NOT assert on log content.** Log emission is operator UX, inspected manually; the test-anchored contract is `received_messages()` (presence vs absence of the message). Log-stream mentions in user-story acceptance scenarios' Then clauses are descriptive, not test assertions. FR-014 is updated to make this explicit (the prior wording's "and on log capture for presence" is removed); SC-002, SC-003, and SC-008 are re-framed so the testable portion (`received_messages()`) is separated from the operator-visible portion (the log entry). This matches the convention 002 established in its FR-011 and FR-014.
- Q: Should `VerifyError` be marked `#[non_exhaustive]`? → A: Yes. FR-014 anticipates `VerifyError` growing (`KeyFormatInvalid`, `AlgorithmMismatch`, etc.) when multi-algorithm verifiers arrive in 011+; marking the enum non_exhaustive means those additions are non-breaking changes for downstream callers, matching the convention used by every major Rust crypto crate's error enum (`ed25519_dalek::SignatureError`, `signature::Error`). This is the rare error enum in the crate that crosses the project's split convention (`MessagePayload`-style growable data enums are non_exhaustive; `ConfigError` / `NetworkError` / `NodeError`-style per-feature error enums are exhaustive); `VerifyError` lands on the non_exhaustive side because its growth is anticipated at the spec level. FR-005 updated with the explicit `#[non_exhaustive]` requirement.
- Q: Which filter runs first on the receive path — signature verification or the 002 topic-subscription filter? → A: Topic filter first, signature verification second. Resolves an internal contradiction in the previous spec wording (FR-013 had said "verification before", US3 AS-4 had said "either order"; with tests-don't-check-logs, neither claim was actually testable). The topic-filter-first ordering avoids signature verification cost on off-topic traffic (negligible for SHA-256 in 003, more material for Ed25519 / BLS in 011+) and preserves 002's pipeline structure (topic filter at the top of the receive loop, verification appended as a post-filter step). Operator-visible consequence: an off-topic + invalid-signature message surfaces as `cause = "topic_not_subscribed"` — the verifier never sees it. FR-013 rewritten to specify the new ordering and rationale; US3 Independent Test step 4 and US3 AS-4 updated to specify `cause = "topic_not_subscribed"` for the both-fail case.
- Cleanup (raised during round-4 audit): US2 AS-3 previously cited `FR-008` for receive-order semantics, which was a referential typo (003's FR-008 is about `generate_keypair`, not ordering). Replaced with an explicit citation to 001's InMemoryNetwork contract and 002's receive-task contract as the source of per-sender FIFO ordering.
- Q (post-plan, surfaced during the design discussion that produced ADR 0010): the original 003 spec treated `Message` as a single struct carrying the §2.3 envelope, implicitly claiming "every protocol message looks like this." That claim is false: ROADMAP features 004 (connection-control), 005 / 010 (peer-sampling), 008 (registry-lookup), and the deferred replication / catch-up will each introduce non-dissemination message types with different field sets. → A: restructure the type hierarchy now (cheaper than after 004+ builds more code on top). `Message` becomes a `#[non_exhaustive]` enum; sole 003 variant `Message::Signed(SignedMessage)`. `SignedMessage` is split into `plain: PlainMessage` + `signature: Signature` — eliminating the placeholder-signature workflow because `signed_bytes` can be computed on `PlainMessage` without the signature field in scope. The 001-era `pubsub_node::network::Envelope { from, message }` routing-wrapper struct is renamed to `RoutingFrame` to free the term "envelope" for prose-level use matching the synthesis §2.3 (where envelope = the whole signed message, signature included). `MessagePayload` is preserved unchanged from 002 — Ping stays as the sole `MessagePayload` variant for now, inside `PlainMessage`. The architectural decision is captured in ADR 0010 (`docs/decisions/0010-protocol-message-type-hierarchy.md`); FR-001, FR-010, FR-011, FR-013, the Assumptions terminology bullet, and the Key Entities section are all updated to match.
- Round-5 audit outcome: a fifth `/speckit-clarify` pass over the spec (after Q6 + cleanup) found **no further spec-level ambiguities**. Verified internal consistency (FR-013 ↔ US3 AS-4 ↔ Independent Test step 4 all agree on topic-filter-first ordering), confirmed every acceptance-scenario claim maps to an FR, confirmed every edge case is either FR-backed or an explicit deferral, and confirmed the dependency graph between `signed_bytes`, `MessageHash`, `signature`, and the `Signer` / `Verifier` traits terminates without circularity. Several near-miss candidates were considered and ruled out as plan-level (test-support helper shape, `Node::new` parameter ordering, `MessageHash::of` exact function signature, `MockCryptoScheme::verifier()` `&self` vs `&mut self`, `Signature` placeholder value during the construct-then-sign workflow, 001/002 test migration pattern, `Cargo.toml` dependency placement, `MessagePayload` variant-tag stability). The spec is plan-ready as of this audit.
- Q (post-plan, surfaced during ADR 0010 drafting): Should `MessageHash::of` consume `&PlainMessage` (hashing the signed-over content only) or `&SignedMessage` (hashing content plus signature)? → A: `&PlainMessage`. The parent-hash chain is content-anchored. Rationale: (i) signature-malleability immunity — chains stay valid across signing-scheme changes (feature 011's Ed25519 swap; any later scheme migration) and across non-deterministic signing schemes (this is the canonical Bitcoin pre-SegWit lesson); (ii) alignment with the Cardano ecosystem convention `tx_hash = blake2b(tx_body)` — body and witnesses hashed separately; (iii) `MessageHash` represents the content's identity, with the signature treated as a separate witness; (iv) cross-language publisher integrations (a future-009-plus concern) only need to agree on the content encoding to interoperate on the chain, not on the signature byte format. Acknowledged counter-argument — wire-level dedup of signature-different / content-identical messages would need a separate hash — does not apply in 003 (no caching, no dedup, no chain validation per N-003) and is flagged for the future feature that first consumes the hash operationally. FR-011 carries the rationale; ADR 0010 captures the full reasoning in its consequences section; `IMPLEMENTATION_NOTES.md` N-005 records the revisit trigger.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Signature Verification on the Receive Path (Priority: P1) 🎯 MVP

A developer instantiates two nodes A and B sharing an InMemory network and a shared verifier. A publisher constructs a `Message` envelope with the §2.3 shape — topic, publisher_id (carrying the publisher's public key), parent_hash (None for the first message), sequence, timestamp, payload, and a signature produced by signing the message's canonical bytes with the matching private key. B sends the message to A. A's receive path verifies the signature using the publisher_id from the envelope; on success, the message appears in A's `received_messages()` snapshot. When the same scenario runs with the signature replaced by arbitrary bytes (or the payload tampered with after signing), A's receive path rejects the message: it does not appear in the snapshot, and A's structured log stream contains a single info-level `event = "message_dropped"` entry with `cause = "invalid_signature"`.

**Why this priority**: This is the irreducible demonstration of the feature — the envelope shape, the verifier on the receive path, the binary contrast between accept-on-valid-signature and drop-on-invalid-signature. Without it, the rest of the feature has no operational meaning.

**Independent Test**: Spawn two nodes A and B sharing an InMemory network, both constructed with `Arc::new(MockCryptoScheme::with_seed([0u8; 32]).verifier())`. Build a `KeyPair` via the same scheme's `generate_keypair`. Construct a signed `Message::Signed(SignedMessage { plain, signature })` whose `plain.publisher_id` carries that KeyPair's public key and whose `signature` is the result of signing `plain.signed_bytes()` with the matching `TestSigner`. Have B send the message to A. Verify A's `received_messages()` snapshot contains exactly that delivery. Then construct a second message identical to the first except for one altered byte in `plain.payload` (without re-signing) and send it to A; verify it does not appear in A's snapshot and that a single info-level `event = "message_dropped"` / `cause = "invalid_signature"` log entry was emitted naming A's self_id, B's peer id, the envelope's topic, and the envelope's publisher_id.

**Acceptance Scenarios**:

1. **Given** node A subscribed to topic `T1`, A constructed with a `TestVerifier`, and a `KeyPair` produced by a `MockCryptoScheme`, **When** B sends to A a `Message` tagged `T1` whose `publisher_id` wraps the KeyPair's public key and whose `signature` is the `TestSigner`-produced signature over the message's `signed_bytes`, **Then** A's `received_messages()` snapshot contains exactly that delivery, attributed to B.
2. **Given** the same setup as Scenario 1, **When** B sends a second message identical to the first except that the `payload` bytes are altered after signing, **Then** A's snapshot does NOT contain the second delivery, AND A's structured log stream contains exactly one info-level entry with `event = "message_dropped"`, `cause = "invalid_signature"`, `self_id` equal to A's peer id, `from` equal to B's peer id, `topic` equal to `T1`, and `publisher_id` equal to the envelope's publisher_id.
3. **Given** the same setup, **When** B sends a third message whose `signature` is replaced with 32 zero bytes (a deliberately bogus signature), **Then** A's snapshot does NOT contain it and the same `message_dropped` / `invalid_signature` log entry is emitted.
4. **Given** the same setup, **When** B sends a fourth message whose `publisher_id` does not match the key used to sign the message (signed with KeyPair X but the envelope claims KeyPair Y's public key), **Then** A's snapshot does NOT contain it and the same drop event is emitted.

### User Story 2 — Multi-Publisher Verification (Priority: P2)

A developer constructs multiple distinct publisher keypairs and emits messages signed by different publishers in turn through a node A subscribed to the relevant topics. A's receive path uses each message's own `publisher_id` to select the verification key — there is no single "node-wide publisher key". Messages signed by their declared publisher land in the snapshot; messages whose declared publisher does not match the signing key are dropped + logged.

**Why this priority**: Generalizes P1's single-publisher demonstration to the multi-publisher case that the protocol is actually for. Confirms that the verifier is keyed off the envelope's `publisher_id` per message, not off any per-node configured key. Lower priority than P1 because P1 already proves the verifier works at all; P2 proves it works the way the protocol requires.

**Independent Test**: Build three keypairs `(P_alice, P_bob, P_carol)` from one `MockCryptoScheme`. Sign one message per publisher tagged with the same topic `T1`. Have a sending node B deliver all three to A (subscribed to `T1`, holding a `TestVerifier`). Verify A's snapshot contains all three deliveries, each with its correct `publisher_id`. Then alter one message's `publisher_id` to a different publisher's public key (without re-signing); verify only the two unaltered messages land in the snapshot, with one `message_dropped` / `invalid_signature` entry for the altered one.

**Acceptance Scenarios**:

1. **Given** three keypairs Alice / Bob / Carol from a single `MockCryptoScheme` and three messages — one signed by each respective publisher — tagged with topic `T1`, **When** B sends all three to A (subscribed to `T1`), **Then** A's snapshot contains all three deliveries in arrival order, each carrying the correct `publisher_id`.
2. **Given** the same three signed messages but with Alice's message's `publisher_id` swapped to Bob's public key (the signature still being Alice's over the original bytes), **When** B sends all three to A, **Then** A's snapshot contains only Bob's and Carol's deliveries; one info-level `message_dropped` / `invalid_signature` entry names Alice's-message-claiming-Bob's-id.
3. **Given** a sequence of at least 50 messages drawn from a pool of 5 distinct publishers, signed by each respective publisher, **When** B delivers them in some interleaved order, **Then** A's snapshot contains exactly the 50 messages, and the per-sender FIFO arrival ordering is preserved as inherited from 001 (the InMemoryNetwork's contract) and 002 (the receive-task contract).

### User Story 3 — Filter Composition with Topic Subscription (Priority: P3)

The 002 topic-subscription filter and the new signature filter compose on the receive path. A message reaches A's snapshot only if (a) A subscribes to the message's topic AND (b) the signature verifies. Both filters drop with the same `event = "message_dropped"` structured tracing event, distinguished by the `cause` field (`cause = "topic_not_subscribed"` for the 002 case, `cause = "invalid_signature"` for the 003 case). The 002-era `event = "topic_drop"` emission is replaced by the new convention in the same commit; no double-emission, no legacy event name.

**Why this priority**: Closes the integration gap with 002. Without this story, a future operator reading logs would see a mix of old (`topic_drop`) and new (`message_dropped`) events, and the convention wouldn't actually be uniform. Lower priority than P2 because the filter mechanics are already established in P1/P2; P3 verifies that they compose correctly and that the project-wide drop-event convention is applied consistently.

**Independent Test**: Construct A subscribed to `{T1}`, holding a `TestVerifier`. Build a `KeyPair` and a valid `TestSigner` for it. Send four messages from B to A:

1. Topic `T1`, signature valid → expected outcome: appears in A's snapshot; no drop event.
2. Topic `T1`, signature invalid → expected outcome: dropped; one `message_dropped` / `invalid_signature` event.
3. Topic `T2`, signature valid → expected outcome: dropped; one `message_dropped` / `topic_not_subscribed` event.
4. Topic `T2`, signature invalid → expected outcome: dropped; one `message_dropped` / `topic_not_subscribed` event (per FR-013's topic-filter-first ordering, the topic filter rejects before the verifier runs; the invalid signature is never observed for this message). Test asserts only on `received_messages()` absence; the operator-visible cause is descriptive.

**Acceptance Scenarios**:

1. **Given** A subscribed to `{T1}` with a `TestVerifier`, **When** B sends a valid-signature on-topic message, **Then** A's snapshot contains exactly that delivery; no `message_dropped` event is emitted.
2. **Given** the same setup, **When** B sends a valid-signature off-topic message (topic `T2`), **Then** A's snapshot does NOT contain it; exactly one info-level `event = "message_dropped"` / `cause = "topic_not_subscribed"` entry is emitted (with `self_id`, `from`, `topic`); no `cause = "invalid_signature"` entry is emitted.
3. **Given** the same setup, **When** B sends an invalid-signature on-topic message, **Then** A's snapshot does NOT contain it; exactly one info-level `event = "message_dropped"` / `cause = "invalid_signature"` entry is emitted; no `cause = "topic_not_subscribed"` entry is emitted.
4. **Given** the same setup, **When** B sends a message that is both off-topic (topic `T2`) and invalid-signature, **Then** A's snapshot does NOT contain it. Operator-visible (descriptive, not test-anchored per FR-014): the structured log stream emits one info-level `event = "message_dropped"` / `cause = "topic_not_subscribed"` entry — per FR-013's topic-filter-first ordering, the topic filter rejects the message before the verifier runs, so the invalid signature is never observed for this message and `cause = "invalid_signature"` is NOT emitted for it.
5. **Given** any of the above drop scenarios, **When** the structured log stream is inspected, **Then** no log entry with `event = "topic_drop"` appears anywhere in the stream — the legacy event name from 002 has been replaced.

### User Story 4 — Reproducible Mock-Crypto Keypairs from a Seed (Priority: P4)

A developer testing signature-verification flows builds a `MockCryptoScheme` from a known 32-byte seed and generates a sequence of keypairs. The byte content of each keypair is fully determined by the seed and the position in the call sequence. Re-running the same test with the same seed produces byte-identical keypairs. Switching to `MockCryptoScheme::from_entropy()` produces non-deterministic keypairs suitable for tests that explicitly want randomness.

**Why this priority**: Tests that assert against specific signature bytes, specific public-key bytes, or the `_public` suffix property of the mock all depend on the keygen being reproducible from a seed. Without this property, those tests become non-deterministic. Lowest priority among the four stories because the other three already cover the externally-visible verify/drop behavior; US4 covers the test-infrastructure property that makes the lower stories reliably testable, plus the explicit escape valve for tests that want fresh randomness.

**Independent Test**: Build two `MockCryptoScheme` instances both via `with_seed([0u8; 32])`. Generate three keypairs from each. Verify the corresponding pairs are byte-identical (`scheme_1.kp1.public == scheme_2.kp1.public`, same for private; same for kp2 and kp3). Build a third scheme via `with_seed([1u8; 32])` and verify its first keypair differs from the first two schemes' first keypair. Build a fourth scheme via `from_entropy()` and verify (statistically — overwhelmingly likely) that its first keypair differs from any of the seeded schemes' first keypairs.

**Acceptance Scenarios**:

1. **Given** two `MockCryptoScheme` instances both constructed via `with_seed(s)` for the same 32-byte `s`, **When** each generates `N` keypairs via successive `generate_keypair()` calls, **Then** for every `i ∈ 0..N`, the two schemes' `i`-th keypairs are byte-identical (same `public.as_bytes()`, same `private.as_bytes()`).
2. **Given** two `MockCryptoScheme` instances constructed via `with_seed(s_1)` and `with_seed(s_2)` for `s_1 ≠ s_2`, **When** each generates its first keypair, **Then** the two keypairs are NOT byte-identical (the seed change propagates into key bytes).
3. **Given** any `MockCryptoScheme` instance, **When** a keypair is generated and inspected, **Then** `derive_public(&keypair.private)` equals `keypair.public` (the public key is derivable from the private by the mock's `_public`-suffix convention).
4. **Given** any keypair generated as above, **When** a `TestVerifier` verifies a `Signature` produced by `TestSigner::new(keypair.private)` over arbitrary bytes `m`, against `keypair.public`, **Then** the verifier returns `Ok(())`.
5. **Given** any keypair generated as above, **When** a `TestVerifier` is asked to verify a signature with `keypair.public` swapped for a `PublicKey` whose bytes do not end in the `_public` suffix, **Then** the verifier returns `Err(VerifyError::Invalid)`.

### Edge Cases

- **First message from a publisher**: a publisher's first message on a topic carries `parent_hash = None`. The signed bytes encode this as 32 zero bytes (`MessageHash::ZERO`). Signature verification proceeds normally; no chain-integrity check fires in 003 (deferred per N-003). Subsequent messages from the same publisher continue to carry `parent_hash = Some(hash_of_previous)` — but 003 stores those messages without inspecting whether the hash matches anything in the arrival log.
- **Empty payload**: a message whose `payload` carries an empty body (zero-length `Ping`, or a future variant with an empty body) is encodable: the length-prefix is zero followed by no bytes. The signature is computed over the canonical bytes including the zero length; verification proceeds normally.
- **`Timestamp` at epoch origin or far future**: `Timestamp::from_millis(0)` (epoch origin) and `Timestamp::from_millis(u64::MAX)` are both valid envelope values. The signature covers the timestamp; verification compares signatures bytes-for-bytes without interpreting the timestamp.
- **`publisher_id` carrying random non-derived bytes**: a `PlainMessage` constructed by a caller bypassing `MockCryptoScheme::generate_keypair` (e.g., test code that writes `PublisherId::from(PublicKey::new(vec![0u8; 8]))` directly into the `plain.publisher_id` field) yields a `PublicKey` whose bytes do not end in `_public`. The verifier's `strip_suffix` returns `None` and `verify` returns `Err(VerifyError::Invalid)`; the receive path drops the message with `cause = "invalid_signature"`. No panic, no error escalation — the drop path handles malformed public keys uniformly with signature mismatches.
- **Replay of an identical signed envelope**: a verifier-valid envelope sent twice (byte-identical, same signature) is accepted twice and appears twice in the receiver's snapshot. 003 does not deduplicate; replay detection is a future concern (the synthesis §2.3 sequence-number-and-hash-chain mechanics support it once chain integrity lands per N-003).
- **Concurrent inbound stream of mixed valid/invalid signatures**: the receive path verifies one message at a time; signature failures on one message do not affect the processing of other messages, and the drop event for an invalid message does not interrupt the arrival order of subsequent valid messages.
- **Self-addressing under signed envelopes**: per N-002, the 002-era self-addressing edge case (a Node emitting a message addressed to its own peer id) is operationally exotic and the receive path treats it as a normal inbound delivery. Under 003 the inbound delivery is additionally signature-verified; a Node that sends itself a signed message will see it appear in its own `received_messages()` if the signature verifies. The N-002 trigger to revisit semantics under connection-based transports (feature 004+) is unaffected by 003.
- **Inherited 002 edge cases**: empty subscription set, re-subscribing / unsubscribing idempotency, duplicate `subscribed_topics` entries in TOML, and the receiver-filter behavior under multi-peer concurrent traffic all carry forward from 002 unchanged. The `subscribed_topics` TOML field is unchanged in 003; no new TOML field is introduced.
- **Inherited 001 edge cases**: sends to unregistered ids continue to be dropped + warn-logged per 001 FR-010; the empty-peer-set case remains valid. 003 layers signature verification on top of 001's substrate; nothing in 001's contract is altered.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The `pubsub_node::Message` type MUST become a `#[non_exhaustive]` enum whose sole 003-era variant is `Message::Signed(SignedMessage)`. `SignedMessage` MUST be a struct carrying two fields — `plain: PlainMessage` and `signature: Signature`. `PlainMessage` MUST be a struct carrying the staged-design-synthesis §2.3 fields (excluding the signature): `topic: TopicId`, `publisher_id: PublisherId`, `parent_hash: Option<MessageHash>`, `sequence: u64`, `timestamp: Timestamp`, `payload: MessagePayload`. The 002-era `MessagePayload` enum (currently a single `Ping(u64)` variant; `#[non_exhaustive]`) is preserved unchanged and lives as a field of `PlainMessage`. The 001-era `pubsub_node::network::Envelope { from: PeerId, message: Message }` routing-wrapper struct MUST be renamed `RoutingFrame` in the same commit; the rename frees the term "envelope" for prose-level use matching the staged-design-synthesis's terminology (the whole signed message, signature included). The `Message` enum, its variant payload structs, and the `RoutingFrame` rename are all governed by ADR 0010 (`docs/decisions/0010-protocol-message-type-hierarchy.md`) — that ADR is the structural record for this layering. Pre-003 message-construction call sites MUST be updated alongside this feature; the migration is mechanical via the `tests/common/mod.rs` helper introduced by the plan.
- **FR-002**: `PublisherId` MUST be a newtype around `PublicKey`, distinct at the type level from `PeerId`. `PublisherId` represents the message originator (the entity whose private key produced the envelope's signature); `PeerId` continues to represent the network neighbor that forwarded the message. Even when both happen to wrap the same `PublicKey` byte representation under a future iteration, the compiler MUST distinguish them — accidental cross-role use MUST be a compile error. `PublisherId` MUST derive `Clone`, `Debug`, `Eq`, `PartialEq`, and `Hash` so it can serve as a `HashMap` key (matching the 001 / 002 convention for `PeerId` and `TopicId`). Future features that key on `PublisherId` (per-publisher chain heads once chain integrity arrives post-N-003; publisher-authorization lookups in feature 008; per-publisher counters / caches) depend on this derive set; deferring it would force a spec amendment when those features land.
- **FR-003**: `PublicKey`, `PrivateKey`, and `Signature` MUST be concrete byte-newtype structs living in `pubsub_node::crypto`. Their internal byte representation is opaque to the rest of the crate; concrete `Signer` / `Verifier` impls choose how to interpret the bytes. None of these types MUST be parameterised by an associated type or generic parameter at the crate's public API surface (per ADR 0009's rejection of the `CryptoScheme`-as-associated-types pattern). Standard-trait derives MUST follow crypto-code discipline:
  - `PublicKey` MUST derive `Clone, Debug, Eq, PartialEq, Hash` (matching the convention used for `PublisherId`, `PeerId`, and `TopicId` — supports use as a `HashMap` key in future features such as publisher-authorization registries).
  - `Signature` MUST derive `Clone, Debug, Eq, PartialEq` (no `Hash` — signatures are not natural map keys; replay or equivocation tracking should key on message-hash or `(publisher_id, parent_hash)` instead). This matches the convention real Rust crypto crates use (e.g. `ed25519_dalek::Signature`).
  - `PrivateKey` MUST derive `Clone, Eq, PartialEq` (no `Hash`, no derived `Debug`). It MUST instead carry a **hand-written `Debug` impl that redacts the byte content** (e.g., outputs `PrivateKey { .. }` or `"PrivateKey([REDACTED])"`), so panics and test-failure messages remain legible without leaking secret bytes. This matches the convention real Rust crypto crates use (e.g. `ed25519_dalek::SigningKey`) and carries the discipline forward to feature 011's Ed25519 swap — where `PrivateKey` will additionally adopt `Zeroize` and constant-time comparison.
  
  `MessageHash` MUST be a fixed-width 32-byte newtype (`MessageHash([u8; 32])`), MUST derive `Clone, Debug, Eq, PartialEq, Hash`, and MUST expose a public `ZERO` constant for use as the absent-`parent_hash` sentinel in `signed_bytes` encoding. `Timestamp` MUST be a newtype around `u64` carrying Unix epoch milliseconds, MUST derive `Clone, Copy, Debug, Eq, PartialEq, Ord, PartialOrd, Hash`, and MUST expose constructors `Timestamp::now()` (resolving the system clock) and `Timestamp::from_millis(u64)` (for caller-controlled values, typically in tests).

  **`Display` format for operator-facing rendering**: `PublicKey`, `Signature`, and `MessageHash` MUST implement `Display` as full **lowercase hex** of their underlying bytes (e.g., `PublicKey` of bytes `[0x70, 0x75]` renders as `"7075"`). `PublisherId`'s `Display` MUST delegate to its inner `PublicKey`'s `Display`. The hex convention matches what real Rust crypto crates use (e.g., `ed25519_dalek::Signature`); it carries forward unchanged when Ed25519 fixed-length keys arrive in feature 011 (FR-018), and produces deterministic output that operators can copy into other tools without translation. `PrivateKey` MUST NOT implement `Display` — the redacting `Debug` from the bullet above is its only stringifying surface, and there is no use case for printing a private key in operator-facing context.
- **FR-004**: A public trait `Signer` MUST be defined in `pubsub_node::crypto` with the shape `fn public_key(&self) -> PublicKey` and `fn sign(&self, msg: &[u8]) -> Signature`. The trait MUST be `Send + Sync`. The trait MUST take no type parameters and MUST NOT define associated types. The `msg` argument MUST be `&[u8]` (raw bytes), so callers can pass the output of `PlainMessage::signed_bytes()` directly without coupling the trait to the `Message` enum or any other domain type. A future `Ed25519Signer` (feature 011) and the v1 `TestSigner` (this feature) MUST both implement the trait without changing its surface.
- **FR-005**: A public trait `Verifier` MUST be defined in `pubsub_node::crypto` with the shape `fn verify(&self, key: &PublicKey, msg: &[u8], sig: &Signature) -> Result<(), VerifyError>`. The trait MUST be `Send + Sync`. The trait MUST take no type parameters and MUST NOT define associated types. `VerifyError` MUST be a typed enum living in `pubsub_node::crypto`; its v1 variant set is `{ Invalid }` (representing "signature does not match key+msg"). The enum MUST be marked `#[non_exhaustive]` so that adding new variants in feature 011+ (`KeyFormatInvalid`, `AlgorithmMismatch`, etc., per FR-014's anticipation) is a non-breaking change for downstream callers — this matches the convention used by every major Rust crypto crate's error enum (`ed25519_dalek::SignatureError`, `signature::Error`, etc.) and is consistent with FR-018's goal that the trait surfaces remain unchanged across the 011 swap. The error MUST implement `std::error::Error`, `Debug`, and `Display` per the crate-wide typed-errors convention (ADR 0005 lineage).
- **FR-006**: A `pubsub_node::crypto::mock` module MUST contain a `MockCryptoScheme` factory struct, a `KeyPair { public: PublicKey, private: PrivateKey }` value type, and concrete `TestSigner` and `TestVerifier` impls. The module MUST be public at the crate boundary so tests and downstream test harnesses can use it; the rustdoc on the module MUST carry a prominent **"MOCK — not unforgeable"** warning paragraph stating that any caller with read access to a `PublicKey` produced by this scheme can forge a signature that the matching `TestVerifier` accepts, and that the mock exists only to differentiate correct/incorrect key+message bindings in tests, not to make any authenticity claim. Real authenticity arrives in feature 011 (`Ed25519Signer` / `Ed25519Verifier`).
- **FR-007**: `MockCryptoScheme` MUST expose `with_seed(seed: [u8; 32]) -> Self` (constructing the scheme with a deterministic ChaCha20 PRNG seeded by the caller-supplied bytes) and `from_entropy() -> Self` (constructing the scheme with a PRNG seeded from OS entropy). Both constructors MUST yield a scheme that holds an internal RNG state; subsequent keypair generation draws from this RNG. The PRNG implementation MUST be `rand_chacha::ChaCha20Rng`, chosen as the standard idiomatic seeded RNG for the Rust ecosystem; the `rand` and `rand_chacha` crates are introduced as new direct dependencies of the crate under this feature.
- **FR-008**: `MockCryptoScheme` MUST expose `generate_keypair(&mut self) -> KeyPair`. Each call MUST draw fresh randomness from the scheme's internal RNG, producing a `KeyPair` whose `private.as_bytes()` is a freshly-drawn 32-byte block and whose `public` is derived from the private by appending a fixed byte suffix (FR-009). Successive calls on the same scheme MUST yield independent key pairs (the RNG advances). Two schemes constructed with the same seed via `with_seed` MUST yield byte-identical keypair sequences across all `generate_keypair` calls.
- **FR-009**: The `TestSigner` / `TestVerifier` mock pair MUST implement the asymmetric-shaped construction described in ADR 0009: `derive_public(&PrivateKey) -> PublicKey` MUST produce a `PublicKey` whose bytes are the private key's bytes concatenated with a fixed suffix `PUBLIC_SUFFIX: &[u8] = b"_public"`. `TestSigner::sign(msg)` MUST produce `Signature(sha256(self.private.as_bytes() || msg))`. `TestVerifier::verify(public, msg, sig)` MUST attempt to strip `PUBLIC_SUFFIX` from `public.as_bytes()`; if the strip fails (the bytes do not end in the suffix), `verify` MUST return `Err(VerifyError::Invalid)`. If the strip succeeds, `verify` MUST recompute `sha256(stripped_bytes || msg)` and compare byte-for-byte against `sig.as_bytes()`; mismatch MUST yield `Err(VerifyError::Invalid)`; match MUST yield `Ok(())`. The `PUBLIC_SUFFIX` constant MUST be declared once and used by both `derive_public` and the verifier's `strip_suffix` so the two operations remain byte-symmetric by construction.
- **FR-010**: `PlainMessage::signed_bytes(&self) -> Vec<u8>` MUST be defined as the single canonical-encoding seam used by both signature production and signature verification. The method lives on `PlainMessage` (the pre-signature content type per FR-001 + ADR 0010), so the `signature` field is structurally not in scope — no placeholder workflow is needed. The byte layout is hand-rolled length-prefixed concatenation: `u32` big-endian length followed by UTF-8 bytes for `topic`, then `u32` big-endian length followed by raw bytes for `publisher_id`'s underlying `PublicKey`, then exactly 32 bytes of `parent_hash` content (the wrapped `MessageHash` bytes if `parent_hash` is `Some`, otherwise the all-zero `MessageHash::ZERO` sentinel), then `sequence.to_be_bytes()` (8 bytes), then `timestamp.as_millis().to_be_bytes()` (8 bytes), then `u32` big-endian length followed by raw bytes for the `payload`'s encoded form. The `payload` encoding for the 002-inherited `MessagePayload::Ping(u64)` MUST be a 1-byte variant tag (`0x00` for `Ping`) followed by the `u64.to_be_bytes()` of the ping value; future variants will append new tag values without altering the existing tags. The signing workflow at the call site is: construct a `PlainMessage`, compute its `signed_bytes`, sign those bytes to produce a `Signature`, then assemble the `SignedMessage { plain, signature }` and wrap it as `Message::Signed(signed)`. The rustdoc on `PlainMessage::signed_bytes` MUST document this byte layout in full (field order, widths, endianness, the `MessageHash::ZERO` sentinel for absent `parent_hash`, the `MessagePayload` variant tags). Treat the rustdoc as part of the protocol surface — changes to the layout require a rustdoc update in the same commit (per IMPLEMENTATION_NOTES.md N-004 guidance). 003 deliberately omits a leading encoding-version byte: with the in-memory network passing Rust `Message` objects directly (not serialized bytes) and sender / receiver always running the same code base, an envelope-level version distinguisher would only ever fire across different builds of the same `TestSigner` / `TestVerifier` pair, which is a test-only artefact. When the encoding swaps to CBOR canonical at feature 009 per N-004, version identification rides on the CBOR scheme's own conventions rather than a hand-rolled tag byte.
- **FR-011**: `MessageHash` MUST be defined as the SHA-256 of a `PlainMessage`'s `signed_bytes` — that is, the hash is taken over the signed-over content only, **not** over the wrapping `SignedMessage` (signature is excluded from the hash input). The associated function `MessageHash::of(plain: &PlainMessage) -> MessageHash` MUST be available so that downstream callers (test harnesses building a chain of messages, future replication logic) can produce the hash that becomes the next message's `parent_hash`. Callers holding a `SignedMessage` reach the hash via `MessageHash::of(&signed.plain)`. The hash algorithm is SHA-256, provided by the `sha2` crate introduced as a new direct dependency under this feature. The hash output width is fixed at 32 bytes regardless of any future change to the canonical encoding. Rationale for hashing `PlainMessage` rather than `SignedMessage`: the parent-hash chain is content-anchored, so it remains valid across signature-format changes (feature 011's Ed25519 swap; any later scheme migration), is immune to signature malleability (the canonical Bitcoin pre-SegWit lesson), and aligns with the Cardano `tx_hash = blake2b(body)` convention that hashes the body separately from witnesses. ADR 0010's consequences section captures the full reasoning; the decision is flagged for revisit when downstream features first consume the hash operationally (chain-integrity validation in 008 / 012; future dedup / caching) — see `IMPLEMENTATION_NOTES.md` N-005.
- **FR-012**: The `Node` constructor MUST accept a new parameter `verifier: Arc<dyn Verifier>` and MUST store it on the Node for the duration of the Node's lifetime. The parameter is required (not optional): a Node MUST be constructed with a non-None verifier, since unsigned messages have no place in the 003 envelope shape. The `Node` MUST NOT add a `signer` field at this iteration. `Node::send` MUST keep its current shape from 002 — it takes an already-built `Message` argument; construction of the signed envelope (including running a `Signer` to produce the `Signature`) is the caller's responsibility (test harnesses today, a future publisher CLI later). Adding a `Signer` field on `Node`, along with the per-publisher chain-head tracking that would make a `Node::send(payload)` ergonomic API possible, is a deliberate non-goal for 003 per ADR 0009.
- **FR-013**: The `Node`'s receive task MUST pattern-match on the incoming `Message` variant. For `Message::Signed(signed)` (the sole 003 variant per FR-001 + ADR 0010), the task MUST run the 002 topic-subscription filter (002 FR-004) **before** invoking signature verification. Concretely: for each inbound `signed: SignedMessage`, the receive task first checks `signed.plain.topic` against the subscription set; on miss, the message is dropped with `cause = "topic_not_subscribed"` (per FR-015) and the verifier is NOT invoked. On hit, the receive task then computes `signed.plain.signed_bytes()` and calls `self.verifier.verify(signed.plain.publisher_id.as_public_key(), &signed.plain.signed_bytes(), &signed.signature)`. **If `verify` returns `Ok(())`**, the message MUST be appended to `received_messages()` per the inherited 001 FR-006 snapshot-append contract (extended by 002 FR-004 with the topic-filter precondition; the `ReceivedDelivery` wraps the full `Message::Signed(signed)` value, not the inner `PlainMessage`). **If `verify` returns `Err(VerifyError::Invalid)`** (or any future variant per FR-005's `#[non_exhaustive]`), the message MUST be silently dropped: it MUST NOT appear in `received_messages()`, MUST NOT trigger any error return to any caller, and MUST NOT be observable through any other in-process snapshot, counter, event stream, or callable API. The drop MUST emit a single structured log entry per FR-014. The topic-filter-first ordering avoids signature-verification cost on traffic the node has no interest in (negligible in 003 with SHA-256, more material when Ed25519 / BLS verifiers arrive in 011+) and preserves the 002 receive-task pipeline structure (topic filter remains at the top of the loop; verification appends as a post-filter step rather than restructuring the loop). Operator-visible consequence: a message that is both off-topic and invalid-signature surfaces as `cause = "topic_not_subscribed"` — the topic filter rejects first; the verifier never sees the message. Future non-`Signed` variants of `Message` (004's connection-control messages, 005 / 010's peer-sampling messages, etc.) will get their own match arms when those features land; 003 introduces only the `Signed` arm and need not include a catch-all (the `#[non_exhaustive]` attribute on `Message` does not force one when only one variant exists).
- **FR-014**: The structured log entry emitted for a signature-verification failure (FR-013's `Err` path) MUST be at info level and MUST include at minimum:
  - A stable event marker: `event = "message_dropped"`.
  - A stable cause discriminator: `cause = "invalid_signature"`.
  - The receiving Node's own peer id (`self_id`).
  - The forwarding peer's logical peer id (`from`).
  - The envelope's topic (`topic`).
  - The envelope's publisher id (`publisher_id`).
  The log entry MUST NOT cite any FR identifier or spec section in operator-facing text (per the project-wide operator-facing-string convention shared with 002 FR-011 and FR-014). The log entry is for operator observability only — it MUST NOT be surfaced through any in-process snapshot, counter, event stream, or other API consumable by tests, and **tests MUST NOT assert on log content**. Acceptance scenarios assert exclusively on `received_messages()` (absence vs presence of the message); log-stream mentions in the Then clauses of user-story acceptance scenarios are descriptive (they describe what an operator sees during the scenario), not test-anchored assertions. This matches 002's pattern (002 FR-011 and FR-014 establish the same convention: log emission is operator UX, the test-anchored contract is the snapshot).
- **FR-015**: In the same commit that lands the FR-014 emitter, the 002-era topic-filter drop emission MUST be renamed: the previous `event = "topic_drop"` MUST become `event = "message_dropped"`, with the new field `cause = "topic_not_subscribed"` distinguishing the cause. All other fields of the 002 emission (`self_id`, `from`, `topic`) MUST remain unchanged. Any 002-era test that filters log capture on `event == "topic_drop"` MUST be updated in the same commit to filter on `event == "message_dropped"` AND `cause == "topic_not_subscribed"`. After this rename, no source file in the crate MUST emit an entry whose event marker is the legacy `"topic_drop"` value; the project-wide receive-path drop convention is `event = "message_dropped"` with a snake_case `cause` field (per the saved memory `feedback_message_dropped_event_convention`). Future drop reasons (post-N-003 chain inconsistencies, format errors, expired messages, etc.) will add new `cause` values rather than new event names.
- **FR-016**: Arrival-time validation in 003 MUST be **signature-only**. The receive path MUST NOT inspect `parent_hash` for chain-integrity correctness, MUST NOT compare `sequence` against any prior message's sequence, MUST NOT detect or report gap conditions (a message with `sequence = N+2` arriving when the publisher's last-seen sequence was `N`), MUST NOT detect or report equivocation (two valid-signature messages from the same publisher with the same `(parent_hash, sequence)` but different `payload`), and MUST NOT check the publisher's authorization against any registry. These observations MAY hold useful information for future features; 003 explicitly defers all of them per IMPLEMENTATION_NOTES.md N-003. The 003 spec's TDD trigger (Constitution Principle II) applies to signature authenticity only — chain-integrity tests do not appear in this iteration because the corresponding behavior does not appear in this iteration.
- **FR-017**: The TOML node-config schema MUST NOT change in 003. The 002-era top-level `subscribed_topics` field, the `[[peers]]` entries, and the strict-unknown-field policy all remain unchanged. Because signing is caller-side (FR-012) and the Node does not hold a `Signer`, no publisher key material is loaded from the TOML at this stage. The `Arc<dyn Verifier>` parameter to `Node::new` is constructed by the binary's `main.rs` and by test harnesses programmatically (typically via `MockCryptoScheme::with_seed(...).verifier()` for tests and a static `TestVerifier` for the binary at this prototype-stage iteration); no configuration knob exposes the choice of verifier in 003.
- **FR-018**: The crypto trait set (`Signer`, `Verifier`, `PublicKey`, `PrivateKey`, `Signature`, `VerifyError`) MUST be designed so that the future swap to real Ed25519 in feature 011 does not change any public API signature in `pubsub_node`. Concretely: the 011 work will add an `ed25519` submodule next to `mock` (with `Ed25519Signer`, `Ed25519Verifier`, and an `Ed25519CryptoScheme`), swap the binary's verifier construction from `MockCryptoScheme::*.verifier()` to `Ed25519CryptoScheme::*.verifier()`, and update the internal byte interpretation of `PublicKey` / `PrivateKey` / `Signature` to match Ed25519's curve representation. The trait surfaces, the `Node::new` parameter shape, the `PlainMessage::signed_bytes` rustdoc-documented byte layout, the `Message` enum shape and its `Signed` variant payload (`SignedMessage`), and the receive-task signature-verification call site MUST remain identical across the swap. Additional 011 work — `Zeroize` and constant-time-comparison on `PrivateKey` — is additive, not breaking, per ADR 0009 + ADR 0010's combined contract.
- **FR-019**: Concurrency semantics for the signature-verification step MUST be linearizable with respect to the rest of the receive path (extending 002 FR-015's linearizability contract to cover signature verification). Specifically, for any inbound message reaching the receive task, the topic-filter check (002 FR-004, ordered first per FR-013), the subsequent signature verification step (FR-013), and the snapshot append on a successful verify (001 FR-006 — extended by 002 FR-004 with the topic-filter precondition) MUST together observe a coherent point in the linearized order of subscription-set mutations (002 FR-006); a `subscribe(T)` returning `Added` on another task MUST be visible to the topic-filter check on any inbound message whose receive-task processing began after the `subscribe` call returned. The receive task processes inbound messages serially (FR-020 single-task model); only the receive task ever appends to `received_messages()`, so the snapshot has a single writer. The verifier MUST be stateless (a unit struct or empty struct) — this preserves the single-writer invariant and leaves the trait surface unchanged when future verifier impls (real Ed25519 in 011) wish to offload CPU-heavy verification per FR-020.
- **FR-020**: The receive-path signature-verification step MUST be confined to the Node's existing receive task (per 002's ADR 0006 receive-task model); 003 introduces no new async task and no new dispatch primitive. Concretely: the receive task's `while let Some(frame) = rx.recv().await { ... }` loop in `src/node.rs` (where `frame: RoutingFrame` per ADR 0010's rename of the 001 `Envelope`) gains a `match frame.message { Message::Signed(signed) => { /* per FR-013's ordering */ } }` pattern-match inside the loop body; the verification step lives inside the `Signed` arm. The verifier call `self.verifier.verify(...)` is synchronous (returns `Result<(), VerifyError>` directly); it MUST NOT introduce an `await` point into the receive task. Future verifier impls (real Ed25519 in 011) that are CPU-heavy enough to warrant offloading MUST do so via their own internal mechanism (rayon, blocking-thread-pool) without changing the trait's synchronous signature. Future non-`Signed` variants of `Message` get their own match arms when those features land (per FR-013's future-extension note).

### Key Entities

- **Message** (reshaped — was a struct in 002, now an enum per FR-001 + ADR 0010): a `#[non_exhaustive]` enum representing the kind of protocol message being exchanged between Nodes. In 003 the sole variant is `Message::Signed(SignedMessage)`; future features (004 connection-control, 005 / 010 peer-sampling, 008 registry-lookup, deferred replication) add their own variants without disturbing dissemination semantics.
- **SignedMessage**: a struct that wraps a `PlainMessage` (the signed-over content) and a `Signature`. Represents a signed dissemination message — the §2.3 envelope shape in the staged-design-synthesis. Carried as `Message::Signed(SignedMessage)` at the protocol layer.
- **PlainMessage**: a struct carrying the §2.3 fields excluding the signature: `topic`, `publisher_id`, `parent_hash`, `sequence`, `timestamp`, `payload`. The canonical-encoding seam `signed_bytes(&self) -> Vec<u8>` lives on this type; the resulting bytes are the input to `Signer::sign` (and to `MessageHash::of` for parent-hash chain anchoring).
- **MessagePayload** (inherited from 002, unchanged): a `#[non_exhaustive]` enum carrying the application-level content of a dissemination message. Sole variant in 003 is `Ping(u64)`, inherited from 001's connection-probe semantics. Future variants (governance updates, DeFi intents, SPO alerts, etc.) extend this enum as protocol use cases materialise; the 002-era pattern of "different application content sharing one envelope shape" is preserved at this layer.
- **RoutingFrame** (renamed from 001's `Envelope`): the network-layer routing wrapper `{ from: PeerId, message: Message }`. The InMemoryNetwork's "from→to" frame; carried unchanged by 003 except for the name (the rename happens in the same commit as the rest of the type-hierarchy changes, per ADR 0010).
- **PublisherId**: a newtype around `PublicKey` identifying the originating entity of a message. Distinct at the type level from `PeerId` (which identifies a network neighbor). At prototype scale the wrapped `PublicKey` bytes ARE the publisher's key material; the future on-chain registry (feature 008/012) will validate the publisher's authorization to publish on a given topic.
- **PublicKey / PrivateKey**: opaque byte-newtype types in `pubsub_node::crypto`. The internal byte representation is interpreted by concrete `Signer` / `Verifier` impls; the trait API itself does not interpret them. v1 mock impls use 32-byte private keys with a `_public`-suffix-appended derivation for the matching public key; future Ed25519 impls use 32-byte private and public keys.
- **Signature**: an opaque byte newtype. v1 mock impls store 32 bytes (the SHA-256 hash output of the signing input); future Ed25519 impls will store 64 bytes (the Ed25519 signature format). Verification compares signatures byte-for-byte against the recomputed expected value.
- **MessageHash**: a fixed-width 32-byte newtype (`MessageHash([u8; 32])`) over the SHA-256 of `PlainMessage::signed_bytes`. Used as the `parent_hash` field's content type on `PlainMessage`. Exposes a `ZERO` constant for use as the sentinel in `signed_bytes` encoding when `parent_hash` is `None`.
- **Timestamp**: a newtype around `u64` carrying Unix epoch milliseconds. Advisory only — the receive-path verifier does not compare timestamps against any clock; the timestamp's only role is to be included in the canonical signing bytes so the publisher's signature commits to a publication time the publisher chose to assert.
- **VerifyError**: a typed enum in `pubsub_node::crypto`. v1 variant set: `{ Invalid }` (signature does not match key+msg). Future variants (e.g., `KeyFormatInvalid`, `AlgorithmMismatch`) are anticipated when multi-algorithm verifiers arrive; the spec's drop semantics treat all `Err` variants uniformly at the receive path under 003.
- **Signer trait**: the abstract signing capability. Mock impl is `TestSigner`; future impl is `Ed25519Signer` (feature 011).
- **Verifier trait**: the abstract verification capability. Mock impl is `TestVerifier`; future impl is `Ed25519Verifier` (feature 011). Stored on `Node` as `Arc<dyn Verifier>`.
- **MockCryptoScheme**: a factory struct in `pubsub_node::crypto::mock` that owns a seeded RNG (`rand_chacha::ChaCha20Rng`) and produces `KeyPair` values plus constructs `TestSigner` / `TestVerifier` instances. Reproducibility from a 32-byte seed is part of its public contract.
- **KeyPair**: a `{ public: PublicKey, private: PrivateKey }` struct returned by `MockCryptoScheme::generate_keypair`. Callers consume the `private` half when constructing a `TestSigner` and embed the `public` half in a message envelope's `PublisherId`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A developer can stand up a two-node signed-message demonstration (US1) — instantiate two Nodes sharing an InMemory network and a shared verifier, construct a signed `Message` via `MockCryptoScheme` + `TestSigner`, send it from one Node to the other, and verify it appears in the receiver's `received_messages()` snapshot — in under 30 seconds of local execution time (excluding build/compile time). Extends 002 SC-001's two-node demonstration to the signed-envelope case.
- **SC-002**: A developer can demonstrate the binary contrast of signature validity (US1) — the same setup as SC-001 but with one byte of the payload altered after signing — and verify that the altered message does NOT appear in the snapshot, in under 30 seconds of local execution time. Operator-visible (not test-anchored, per FR-014's tests-do-not-check-logs convention): the structured log stream gains a single info-level `event = "message_dropped"` / `cause = "invalid_signature"` entry on each rejection, observable when the operator inspects the log stream manually.
- **SC-003**: A developer can demonstrate filter composition (US3) — a node subscribed to `{T1}` with a verifier, receiving four messages spanning the on-topic/off-topic × valid-signature/invalid-signature matrix — and verify that exactly the valid-on-topic message appears in `received_messages()` (the other three are absent). The test-anchored verification is zero false-positive deliveries and zero false-negative drops in `received_messages()`. Operator-visible (not test-anchored): each of the three dropped messages emits exactly one `event = "message_dropped"` entry with the correct `cause`, and no log entry carries the legacy 002 `event = "topic_drop"` name (verified manually by grepping the log stream or the crate's source per SC-007).
- **SC-004**: A new contributor reading `specs/003-message-envelope-mock-crypto/spec.md` together with the directory's `quickstart.md` can reproduce the four-message filter-composition demonstration within one hour, without consulting `plan.md`, `research.md`, `contracts/`, ADRs, or any document outside the feature directory. Amendments to this spec that affect contributor-facing behaviour (FRs governing the envelope shape, the `Signer` / `Verifier` trait surfaces, the `MockCryptoScheme` factory API, the `message_dropped` event shape, or the test names referenced in `quickstart.md`) MUST land alongside the corresponding `quickstart.md` updates in the same commit; reviewers SHOULD reject a spec amendment that leaves `quickstart.md` outdated. Extends 002 SC-004's spec-quickstart cohesion rule.

Two instances constructed with different seeds MUST yield differing first keypairs. Verified by direct unit tests on the `crypto::mock` module.
- **SC-006**: The mock crypto module's "MOCK — not unforgeable" warning is rustdoc-visible at the module, struct, and trait levels. The warning text MUST appear in the rustdoc for `pubsub_node::crypto::mock` (module-level), `MockCryptoScheme` (struct), `TestSigner` (struct), and `TestVerifier` (struct). Verified by running `cargo doc` and inspecting the generated HTML, or equivalently by grepping the rustdoc source for the warning phrase in each of the four locations.
- **SC-007**: The 002 `topic_drop` rename is complete and atomic in the same commit as the new `invalid_signature` emitter lands. After the commit, `grep -r "topic_drop"` across the crate's source returns no production-code matches (test fixtures comparing against the new event name are acceptable; the legacy event name MUST NOT appear in any emitter call site or in any operator-visible log output). Verified by repository grep and by re-running 002's integration tests with the new event-name assertion.
- **SC-008**: The signature-verification drop event is operator-observable at default log-level configuration. Running US1's invalid-signature scenario with the default log level surfaces the `event = "message_dropped"` / `cause = "invalid_signature"` entry in the process's log stream — operators do not need to bump verbosity beyond the default. This is an operator-UX criterion, verified by manually inspecting the log stream during the SC-001 / SC-002 demonstration; it is not a test-anchored assertion (per FR-014's tests-do-not-check-logs convention). Symmetric to 002 SC-006 for the topic-drop case.

## Assumptions

- **Terminology after ADR 0010: "envelope" in prose = the whole signed message; Rust types are `Message` / `SignedMessage` / `PlainMessage` / `MessagePayload`; 001's routing wrapper renamed to `RoutingFrame`.** The staged-design-synthesis §2.3 uses "envelope" for the whole signed message (signature included). Throughout this spec, prose-level "envelope" or "message envelope" matches the synthesis meaning — equivalent to `SignedMessage` in the Rust type system after the 003 restructure. The Rust type names are: `Message` (`#[non_exhaustive]` enum of protocol-message kinds, sole 003 variant `Message::Signed(SignedMessage)`); `SignedMessage` (struct: `plain: PlainMessage`, `signature: Signature`); `PlainMessage` (struct carrying the §2.3 fields minus the signature — `topic`, `publisher_id`, `parent_hash`, `sequence`, `timestamp`, `payload`); `MessagePayload` (002's `#[non_exhaustive]` enum, sole variant `Ping(u64)`). The 001-era `pubsub_node::network::Envelope { from: PeerId, message: Message }` routing-wrapper struct is renamed to `RoutingFrame` in the same commit — it remains the network layer's "from→to" frame for the in-memory pipe; the rename frees the term "envelope" for prose-level use matching the synthesis. What gets signed is a `PlainMessage` (the canonical `signed_bytes`); the resulting `Signature` is wrapped alongside the `PlainMessage` into a `SignedMessage`, which is then carried as the `Signed` variant of `Message` on the wire (the `RoutingFrame` carries it onward to the receive task). See ADR 0010 (`docs/decisions/0010-protocol-message-type-hierarchy.md`) for the structural decision and the rationale that motivated this layering.
- **Mock crypto is not unforgeable.** The `TestVerifier` can derive a `PrivateKey` from any `PublicKey` produced by the mock (by stripping the `_public` suffix), so anyone with read access to the mock's module source can produce a forged signature that the verifier accepts. This is a deliberate property of a mock: it makes the trait surface look like real asymmetric crypto without imposing the implementation complexity. Real authenticity arrives in feature 011 (`Ed25519Signer` / `Ed25519Verifier`). The "NOT UNFORGEABLE" warning is loud in rustdoc at multiple locations (SC-006).
- **No publisher-key registry yet.** A node cannot validate that the `publisher_id` on a message is authorized to publish on the message's topic. The signature-only validation in 003 means a node will accept any valid-signature message regardless of whether the publisher key has any standing in the system. Authorization checks layered on top of signature verification are deferred to feature 008 (mock registry) and feature 012 (real on-chain registry) per IMPLEMENTATION_NOTES.md N-003.
- **No chain-integrity validation at the receive path.** Parent-hash linkage, sequence monotonicity, gap detection, and equivocation detection all require chain state (per-`(topic, publisher)` head tracking, or stateless queries over the arrival log) that has no consumer in 003. The envelope fields are *present* so future features can interpret them, but nothing in 003 reads them beyond `publisher_id` (consumed by the verifier). The deferred logic is recorded in N-003 with revisit triggers at features 008 and 012.
- **Signing happens caller-side.** `Node::send` continues to take an already-built, already-signed `Message`. Tests build envelopes by hand (or via a small test-support helper); a future publisher CLI (post-008) will assemble envelopes in its own process and hand them to `Node::send`. No `Signer` field on `Node` and no per-publisher chain-head tracking on `Node` in 003.
- **No replay detection.** A byte-identical signed envelope received twice is accepted twice. Replay detection would consume the same chain state as integrity validation and is similarly deferred.
- **No persistence.** The arrival log lives in memory for the Node's lifetime (per 002's contract); 003 does not change persistence semantics. A future persistence ADR will govern how stored signed messages, if any, are encoded on disk and how key material for `Ed25519Signer` is stored.
- **Canonical encoding is hand-rolled and swap-ready.** The `PlainMessage::signed_bytes` body is hand-rolled length-prefixed concatenation; no leading version-tag byte (003 has no scenario where one would fire — see FR-010 final sentence). The swap to CBOR canonical (RFC 8949 §4.2.2) is deferred to feature 009 (TCP transport) or first cross-language consumer per IMPLEMENTATION_NOTES.md N-004. The swap is a single-seam edit: the call sites for `signed_bytes` do not change; the CBOR scheme carries any future version identification natively.
- **Hash function is SHA-256.** `MessageHash` is SHA-256 of `signed_bytes`. The choice of hash function is not parameterised at this iteration; if a future feature needs blake3 or sha3 it adds a new internal seam, not a public type parameter on `MessageHash`.
- **PRNG is `rand_chacha::ChaCha20Rng`.** The mock keypair generation uses ChaCha20 seeded from a 32-byte seed (or OS entropy via `from_entropy`). Both `rand` and `rand_chacha` are introduced as new direct dependencies under this feature; both are widely-used standard Rust crates per the Constitution's justified-dependencies guidance.
- **`sha2` crate is introduced.** SHA-256 is provided by the `sha2` crate (RustCrypto family), introduced as a new direct dependency under this feature. The crate is vetted and ubiquitous; the alternative of rolling a SHA-256 implementation by hand is explicitly rejected.
- **Inherits all 001 + 002 assumptions.** Trust assumption, liveness assumption, single-process scope, configuration trust, no failure handling, InMemoryNetwork as a dumb pipe, parse-at-the-edge layering, etc. all carry forward. 003 layers signature verification on top of 001's substrate and 002's topic filter; nothing in either prior contract is altered except the explicit 002 `topic_drop` rename per FR-015.
- **No new CLI flag.** The `Arc<dyn Verifier>` parameter is constructed programmatically in `main.rs` (and in test harnesses); 003 does not introduce a `--verifier` flag or any operator-facing configuration knob for choosing the verifier impl. When real Ed25519 lands in 011, the choice between mock and real verifier may surface as a config-time concern; in 003 the binary unconditionally uses the mock verifier at the prototype-stage iteration.
- **Drop-event convention applies workstream-wide.** The `event = "message_dropped"` + `cause` field shape established by FR-014 and the 002 rename in FR-015 is recorded as a project-wide convention in saved memory (`feedback_message_dropped_event_convention.md`). Any future receive-path drop reason (post-N-003 chain inconsistencies, future format errors, etc.) MUST add a new snake_case `cause` value rather than a new event name.
