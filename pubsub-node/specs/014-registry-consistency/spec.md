# Feature Specification: Cross-Registry Consistency Invariant + Declarative Topic Entry

**Feature Branch**: `014-registry-consistency` (spec directory `014-registry-consistency` — feature ID per `specs/ROADMAP.md`)

**Created**: 2026-06-15

**Status**: Draft

**Input**: User description: "Build on the merged 013 topic registry (PR #55) to enforce cross-registry consistency between the topic registry and the node's subscription list, and to refactor the topic entry into a declarative type. Team premise: on-chain contracts validate that a subscription can only reference a registered topic, and the chain follower processes the two registries' events in chain order, so the node — a faithful follower — should rely on and preserve the invariant `state.subscriptions ⊆ state.registered_topics.keys()`. The two registries remain separate artifacts (no merge); consistency is achieved by event ordering plus cascade. Scope: (1) maintain the invariant in `NodeState` with cascade-on-delete (a topic removal drops that topic from the node's subscriptions and any per-topic connection state) rather than leaving inconsistent intermediate states; (2) replace the inline empty-publisher-set 'open topic' check with a declarative `TopicEntry` type (`is_open`/`is_publisher_authorized`, extensible to owners), plus the related registry data-structure cleanup. Out of scope: applying the invariant to 004-connections' acceptance path (004 is unmerged — lands on its rebase); merging the two registries."

## Clarifications

### Session 2026-06-18 — snapshot-reshaped watch + `Synced` lifecycle

Maintainer review after (b): *why keep two `SnapshotComplete` markers at all?* The node only cares about **one** thing — that it is synced (both registries up to date). The markers existed only to delimit each watch's streamed initial burst. Removing them means delivering the initial state as a snapshot instead of a burst — which is also more faithful to a real chain indexer. This supersedes the (b) markers/dial mechanism in FR-005/FR-005b below (the requirement text now reflects this decision).

- Q: Do we need two `SnapshotComplete` markers, or just one "synced" signal? → A: **One signal — reshape the watch to a snapshot.** Both `watch()` methods now return `(snapshot, live-watch)` (`TopicSnapshot`/`MembershipSnapshot`); the in-band burst-end markers (`TopicRegistryEvent::SnapshotComplete`, `MembershipEvent::SnapshotComplete`) are **removed**. The registry indexer folds the topic snapshot then the membership snapshot, then pushes one new **`Event::Synced`**.
- Q: How is "synced" modelled in the node? → A: **An explicit `Syncing → Synced` lifecycle.** `NodeState` gains `synced: bool` (exposed via `Node::is_synced()`); folding `Event::Synced` flips it on the rising edge and establishes connections (`handle_connection_setup`), idempotently. `Event::ConnectionSetup` is retained as the dial **action** (tests / operator / future epochal re-dial). This is the forward-compatible model — a real indexer can fall behind and re-enter `Syncing`.

### Session 2026-06-17 (b) — single-indexer readiness collapse

Maintainer review after the rebase: the first as-built used **two** `SnapshotComplete` events — `TopicRegistryEvent::SnapshotComplete` (a fold no-op, present only to drive the readiness oneshot) and `MembershipEvent::SnapshotComplete` (the dial trigger). That asymmetry modelled two independent chain read-positions, but a realistic prototype follows the chain with a **single indexer** with one "caught up to tip" moment. The readiness signal is collapsed to match. This supersedes the FR-005 / FR-005b mechanism recorded in the 2026-06-17 (rebase) session below (the requirements text now reflects this decision).

- Q: Two `SnapshotComplete` events, one of which folds to nothing — why, and should they merge? → A: **Merge to a single-indexer reader.** Replace the two reader producers + the in-node oneshot with one `registry_indexer_loop` that owns both watches and drains the **topic** burst before the **membership** burst — cold-start ordering becomes intrinsic to the reader's sequence (no oneshot). After both bursts it pushes the **existing** `Event::ConnectionSetup` (the single dial trigger; **no new node-`Event` variant**). The per-stream `SnapshotComplete` markers are retained as the **stream-replay delimiters each mock watch emits**, consumed by the indexer and never enqueued — both fold arms become symmetric no-ops.
- Q: Does this merge the registries? → A: **No.** Only the *readiness signal* collapses; the topic registry and subscription list stay distinct data artifacts with distinct watches (FR-009). 012's single indexer will emit the one readiness directly.

### Session 2026-06-17 (rebase onto merged 004-connections — scope expansion)

Mid-implementation, **004-connections merged to `main`** (PR #56). 014 was rebased onto it, which expands this feature's scope and resolves an item that was previously deferred:

- Q: 004 is now on `main` (connection state, `connection_setup_delay` timer, key-backed `PeerId` all present). Does the connection-state cascade stay deferred? → A: **No — it is now in scope (FR-010 flips).** The `upstream`/`downstream` fields exist, so a topic-registry `Removed` MUST cascade into them too (no connection survives a topic that no longer legitimately exists). The S7 / N-015 cross-registry gap is **resolved here**, not deferred: under strict drop an unregistered topic is never subscribed/candidate, so a connection request on it is now **rejected** (acceptance is consistent with registration).
- Q: The node needs to know when to start establishing connections (sending requests); 004 uses a wall-clock `connection_setup_delay` timer. Should the membership stream carry a readiness signal instead? → A: **Yes.** Add **`MembershipEvent::SnapshotComplete`** (symmetric with `TopicRegistryEvent::SnapshotComplete`): when the membership cold-start burst completes, the node's subscription + candidate view has converged, so the fold runs the connection-selection diff and dials (event-driven establishment). This **replaces** the `connection_setup_delay` timer, which is **removed** — event-driven readiness is strictly better than a guessed delay and removes a wall-clock dependency (reproducibility standard). `Event::ConnectionSetup` itself stays (the establishment mechanism, now triggered by readiness or external injection).
- Q: How is the readiness gate (topic-registry-warm-before-membership) realised now? → A: An in-node **oneshot signal** between the two readers: the topic-registry reader signals once it has enqueued its `SnapshotComplete`; the membership reader holds its events until that signal. The single FIFO event queue then guarantees the topic burst is folded before any membership event. (This is the as-built form of FR-005's "readiness gate"; it stays within the watch-only model and generalises to 012's async chain-sync.)

### Session 2026-06-15

These resolutions follow a design discussion with the maintainers (the PR #55 review conversation, summarised in the team meeting notes of 2026-06-15) and supersede the read-time-intersection model of 013.

- Q: The consistency between the two registries originates on-chain — should the node **assume** it or **validate** it? → A: **Validate it in the node.** The chain follower (indexer) publishes the two registries' events to the node queue **in chain order**, so consistency is *sourced* there: a topic is registered before any subscription references it, and a topic deletion and its subscription deletions arrive in order. But the node does not blindly assume this — the client-side node code **drops incoming events that fail the invariant**, enforcing `subscriptions ⊆ registered_topics` on its own state. The chain ordering is *why* this is sound in production; the node dropping violations is the defensive enforcement.
- Q: Concretely, when the node folds a self-subscription naming a topic that is **not currently registered**, what does it do? → A: **Strict drop.** The node maintains a **single** subscription set that is always a subset of the registered topics; it does **not** keep a separate declared/pending buffer. A membership event that would add (or that names) an unregistered topic is **dropped** for that topic — the topic is not admitted to the subscription set — and an operator log line records it (cause: topic not registered). There is no later auto-promotion: under the chain-order guarantee a subscription only ever arrives after its topic's registration, so a drop signals a genuine ordering/indexer fault, not a transient to recover from. **013 SC-004's "subscribe-before-register → becomes effective" dynamic is removed**, replaced by the ordering guarantee. A topic **removal cascades atomically**: within the single `apply` fold of `Removed`, the topic is dropped from the subscription set, from the per-topic candidate map, and from the registered-topics projection together — no inconsistent intermediate state.
- Q: Strict drop requires the node to fold topic-registration before subscription, but the mock's two registry watches race at cold start (there is no chain follower to order them). How is that ordering guaranteed? → A: **Pull a minimal cross-stream ordering guarantee into this feature.** The node MUST establish topic-registry readiness (a warmed `registered_topics` projection) **before** it begins folding membership events, so that a subscription is always evaluated against an up-to-date registered set and strict drop is correct end to end in the mock. The exact mechanism — seed the registered-topics snapshot synchronously at construction, or gate the membership fold on a topic-registry cold-start "ready" marker — is a `/speckit-plan` decision (it un-defers a minimal slice of the deferred "registry synchronization complete" event). This keeps the two registries separate (no merge) while giving the node the ordering strict drop depends on.
- Q: Should the **topic-registry fold itself** be defensive (not just the subscription side)? Today (013) a `PublishersChanged` for a topic with no prior `Registered` auto-creates it (`or_default`). → A: **Yes — make the registry fold defensive too.** Only a `Registered` event may create a topic in the `registered_topics` projection. A `PublishersChanged` for a topic that is not currently registered is **dropped and logged** (cause: topic not registered), not auto-created; a `Removed` for an unknown topic is a no-op. This makes "validate, don't assume" uniform across both streams. FR-008's "preserve 013 fold semantics" is **amended** accordingly, and the 013 `or_default` fold test is reworked.
- Q: Strict drop is specified for the node's **own** subscriptions; should registration-gating apply symmetrically to the **candidate** sets (other nodes' subscriptions, used by 004's dialing)? → A: **Yes — gate candidates too.** When folding another node's membership, a (peer, topic) candidate is recorded **only if** the topic is currently registered; a candidate naming an unregistered topic is dropped and logged. Combined with the `Removed` cascade (FR-002), `candidates`' topics are always a subset of the registered topics — symmetric with the self-subscription invariant, and it hands 004 a candidate set containing only registered topics.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — The Node Never Holds a Subscription to an Unregistered Topic (Priority: P1) 🎯 MVP

The node maintains, as a property of its own state, the invariant that the topics it considers itself subscribed to are always a subset of the topics the registry says legitimately exist. When the topic registry reports a topic **removed**, the node does not merely stop *accepting* traffic on it at read time — it immediately **drops** that topic from its subscription set (and from the per-topic candidate sets it tracks for other nodes), leaving no intermediate state in which the node still records a subscription to a topic that no longer legitimately exists. The cross-registry consistency that on-chain validation guarantees becomes a maintained, observable property of the node, not only a filter applied when a message arrives.

**Why this priority**: This is the consistency guarantee the feature exists to provide and the precondition the connection model (004) will rely on: if `subscriptions ⊆ registered_topics` holds at all times, acceptance/dialing logic can trust subscription membership without re-checking registration. It is the irreducible behavioural change; the declarative refactor (US2) is supporting.

**Independent Test** (pure, synchronous): Construct `NodeState` for self-id `S`. Fold a topic-registry burst registering `weather` and `sports`, then a self-`Joined { S, {weather, sports} }`. Assert `S`'s subscription set is `{weather, sports}` and the invariant holds (`subscriptions ⊆ registered_topics.keys()`). Separately, fold a self-`Joined { S, {weather, ghost} }` against a state where only `weather` is registered; assert `ghost` is **dropped** (never enters the subscription set) — strict drop. Then fold `Removed { weather }`; assert `weather` is **gone from the subscription set** and from any candidate set keyed on `weather`, the invariant still holds, and a subsequent message on `weather` is dropped. Assert every `apply` returns an empty `Vec<Effect>`.

**Acceptance Scenarios**:

1. **Given** a node subscribed to `{weather, sports}` with both registered, **When** `weather` is removed from the topic registry, **Then** within that single fold `weather` leaves the subscription set, the candidate map, and the registered-topics projection together (atomic cascade), the invariant `subscriptions ⊆ registered` holds, and subsequent messages on `weather` are dropped.
2. **Given** the node from AS-1, **When** the candidate set for `weather` held members (other nodes), **Then** the `weather` removal also clears those `weather` candidates, so no per-topic state survives for the removed topic.
3. **Given** a node and a topic registry in which `ghost` is **not** registered, **When** a self-membership event names `ghost`, **Then** `ghost` is dropped (not added to the subscription set) and recorded in an operator log (cause: topic not registered); a later `Registered { ghost }` does **not** retroactively add `ghost` (no auto-promotion — a fresh membership event after registration is required).
4. **Given** a node brought up against pre-populated topic and subscription registries (cold start), **When** it converges, **Then** topic-registry readiness is established before membership is folded, so every subscribed topic is evaluated against the warmed registered set and no subscription is spuriously dropped by a cold-start race.
5. **Given** a node subscribed to `{weather}` that stays registered, **When** the topic registry never removes `weather`, **Then** message-acceptance behaviour is identical to the merged 013 baseline (no regression for the steady state).

### User Story 2 — Topic Openness and Publisher Authorization Are Expressed Declaratively (Priority: P2)

The rule "a topic with no listed publishers is *open* — any publisher may publish; otherwise the publisher's key must be among the listed publishers" is expressed once, as named, intention-revealing operations on a dedicated topic-entry type, rather than as an inline emptiness-and-membership check buried in the message-receive path. A reader of the accept path sees `entry.is_open()` / `entry.is_publisher_authorized(key)` instead of `set.is_empty() || set.contains(key)`. The type is the single place additional per-topic governance facts (owners, etc.) will attach later without reshaping every call site.

**Why this priority**: A maintainability and correctness refactor explicitly requested in review — the inline check took a reviewer minutes to recognise as the open-topic rule. It removes a class of "is the empty set open or closed?" mistakes by making the intent a method. Lower priority than US1 because it changes expression, not observable accept/drop behaviour.

**Independent Test**: Unit-test the topic-entry type directly: an entry with an empty publisher set reports `is_open()` true and authorizes any key; an entry with `{pubK1}` reports `is_open()` false, authorizes `pubK1`, rejects `pubK2`. Then assert via the pure receive path that accept/drop outcomes for open topics, restricted topics, authorized publishers, and unauthorized publishers are **identical** to the 013 baseline (the refactor is behaviour-preserving).

**Acceptance Scenarios**:

1. **Given** a topic entry with an empty publisher set, **When** its openness is queried, **Then** it reports open and authorizes every publisher key.
2. **Given** a topic entry with a non-empty publisher set `{pubK1}`, **When** authorization is queried, **Then** it reports not-open, authorizes `pubK1`, and rejects any key not in the set.
3. **Given** the declarative type wired into the receive path, **When** the full accept/drop matrix from 013 (open / restricted / authorized / unauthorized / unsubscribed / unregistered) is exercised, **Then** every outcome matches the 013 baseline (no behavioural regression).

### Edge Cases

- **Topic removed while subscribed (the headline cascade)**: within the single `apply` fold of `Removed`, the topic leaves the subscription set, the candidate map, and the registered-topics projection together (atomic); in-flight and subsequent messages on it are dropped. No intermediate state in which a subscription survives for an unregistered topic.
- **Topic removed then re-registered**: after a removal the topic is gone from the subscription set and not retained anywhere (strict drop — no declared buffer). Re-subscription requires a fresh membership event *after* the re-registration; the chain follower's ordering guarantees that ordering in production.
- **Subscription arrives before its topic's registration**: under the chain-order guarantee + the node's topic-registry-readiness gate this does not occur in normal operation. If it nonetheless does, the node **drops** the subscription for that topic and surfaces an operator log (cause: topic not registered) — a signal of a genuine ordering/indexer fault, not a transient the node recovers from. (Contrast 013, which held + masked at read time; that behaviour, including 013 SC-004, is removed.)
- **Cold-start cross-stream race (mock)**: the two registry watches have no inherent ordering; this feature's topic-registry-readiness gate ensures the registered set is warm before membership is folded, so strict drop does not spuriously fire during warm-up. This is the minimal slice of the deferred "registry synchronization complete" mechanism that strict drop requires.
- **Open topic vs absent topic**: unchanged from 013 — a registered topic with an empty publisher set is *open* and subscribable; an unregistered topic is invalid. The declarative `is_open()` makes the first case explicit; the invariant makes the second unrepresentable in the subscription set.
- **PublishersChanged on a registered topic**: unchanged authorization semantics; the publisher set is now mutated through the topic-entry type rather than a bare set, with identical observable results.
- **PublishersChanged / Removed for an unknown topic**: defensive — a `PublishersChanged` for a topic with no prior `Registered` is dropped + logged (no auto-create, replacing 013's `or_default`); a `Removed` for an unknown topic is a no-op. Only `Registered` creates a topic in the projection.
- **Candidate (other node) on an unregistered topic**: dropped + logged, not recorded — symmetric with self-subscription strict drop, so the candidate map's topics stay a subset of the registered topics.
- **Connection-state cascade (in scope post-rebase, 2026-06-17)**: the `Removed` cascade also drops the removed topic's `upstream`/`downstream` connection entries, in the same atomic fold — no connection outlives a topic's legitimacy (FR-002/FR-010). (Originally deferred while 004 was unmerged; now implemented since 014 rebased onto merged 004.)
- **Candidates for a removed topic**: cleared by the cascade (no legitimate participants on a topic that no longer exists), keeping `candidates` consistent with `registered_topics`.

## Requirements *(mandatory)*

### Functional Requirements

#### The maintained consistency invariant (strict drop)

- **FR-001**: The node MUST maintain a **single** subscription set in `NodeState` that is, at every point between event folds, a subset of the registered-topics set (`subscriptions ⊆ registered_topics.keys()`). The same subset invariant MUST hold for the **candidate** map's topics (`candidates.keys() ⊆ registered_topics.keys()` — FR-003a). The merged-013 behaviour of storing a possibly-inconsistent subscription set and computing the effective accept-filter as a read-time intersection (`subscriptions_snapshot`) MUST be replaced by this maintained invariant: the stored subscription set is itself always consistent, with no separate declared/pending buffer.
- **FR-002**: When the node folds a topic-registry `Removed { topic }` event, it MUST **cascade atomically within that single `apply` fold**: remove `topic` from the subscription set, from the per-topic candidate map, from the registered-topics projection, **and from both connection structures** (`upstream` and `downstream`) — every connection entry keyed on the removed topic (FR-010). After the fold no node-state structure may retain an entry keyed on the removed topic, and no intermediate state in which some-but-not-all structures dropped it is observable (the fold runs synchronously under the state lock — ADR 0012). This MUST hold whether or not the node was subscribed to the topic.
- **FR-003**: The node MUST enforce the invariant by **dropping** events that would violate it rather than assuming the streams are well-ordered (Clarifications, Session 2026-06-15). When folding a self-membership event (`Joined`/`TopicsChanged`) that names a topic **not** currently in `registered_topics`, the node MUST NOT add that topic to the subscription set (strict drop) and MUST NOT retain it for later promotion. There is no auto-promotion: a topic registered after the dropped subscription requires a fresh membership event to be subscribed (guaranteed by the chain follower's ordering in production). This removes 013's SC-004 "subscribe-before-register → becomes effective" dynamic.
- **FR-003a**: Strict drop MUST apply symmetrically to the **candidate** fold: when folding another node's membership (`Joined`/`TopicsChanged`), a (peer, topic) candidate MUST be recorded **only if** `topic` is currently registered; a candidate naming an unregistered topic MUST be dropped (not recorded) and logged. Together with the `Removed` cascade (FR-002), this maintains `candidates.keys() ⊆ registered_topics.keys()` at all times.
- **FR-003b** (the shared operator-visibility clause for FR-003 and FR-003a — not a third drop rule): whenever a self-subscription topic (FR-003) or a candidate topic (FR-003a) is dropped for being unregistered, the node MUST emit one operator log line (cause: topic not registered) surfacing the topic, so a genuine indexer/ordering fault is observable. This is defensive enforcement visibility, not a construction failure. (Logs are operator UX, never a test surface — Constitution.)
- **FR-004**: The invariant MUST be enforced dynamically as either stream changes, without restart: a `Removed` cascades (FR-002); a `PublishersChanged` updates authorization (FR-008); a membership change is admitted only for registered topics (FR-003). The node MUST NOT depend on a read-time intersection to mask inconsistency. Pre-existing 013 behaviours that assumed the read-time-intersection model — including **013 SC-004** (the subscribe-before-register dynamic; distinct from *this* spec's SC-004, which is the accept/drop-matrix preservation criterion) — are superseded; the affected tests MUST be reworked (FR-012).

#### Cross-stream ordering (the readiness gate strict drop depends on)

- **FR-005**: Because strict drop (FR-003) evaluates each subscription against the *current* registered set, the node MUST establish **topic-registry readiness** — a warmed `registered_topics` projection — **before** it folds membership events, so a subscription is never spuriously dropped at cold start. **As built (2026-06-18):** each `watch()` returns a current-state **snapshot** (`TopicSnapshot`/`MembershipSnapshot`) plus a live-delta stream; a **single registry indexer** folds the **topic snapshot before the membership snapshot**, so ordering is **intrinsic to the one reader's sequence** — no cross-stream primitive. The two registries stay **separate** streams (no data merge, FR-009); only the readiness signal is unified. This models the single chain indexer of a realistic deployment (query state at tip, then subscribe — 012 returns its at-tip snapshot the same way).
- **FR-005a**: The single public subscriptions getter MUST return the node's maintained subscription set (the message accept-filter) directly — it is, by FR-001, already the consistent effective set, so the getter no longer performs a read-time intersection. The observable contract is unchanged from 013's collapsed `subscriptions()`.
- **FR-005b** (readiness lifecycle + dial): once both registry snapshots are folded, the registry indexer MUST push a single `Event::Synced`. Folding `Event::Synced` MUST transition the node `Syncing → Synced` (`NodeState.synced`, exposed via `Node::is_synced()`) on the rising edge and establish connections (the connection-selection diff `handle_connection_setup`, returning the dial `Request`s); it MUST be idempotent (a redundant `Synced` re-emits nothing). This **replaces** 004's wall-clock `connection_setup_delay` timer, which MUST be **removed** (config field, TOML key, timer producer). `Event::ConnectionSetup` is retained as the dial **action** (tests / operator injection / future epochal re-dial); `Synced` is the lifecycle transition that invokes it.

#### The declarative topic entry

- **FR-006**: A topic's authorized-publisher information MUST be represented by a dedicated topic-entry type rather than a bare publisher-key set exposed at call sites. The type MUST wrap the authorized-publisher set and expose intention-revealing operations, at minimum: an openness predicate (true when no publisher restriction applies — the empty-set case) and a publisher-authorization predicate (`authorized for key` = the topic is open OR the key is in the authorized set). The type MUST be the extension point for future per-topic governance fields (owners, admins, …) so adding them does not reshape call sites (forward-compatible-interface standard; the 011/012 consumers justify the seam).
- **FR-007**: The inbound signed-message authorization check (currently the inline `authorized.is_empty() || authorized.contains(key)` in `handle_signed_message`) MUST be expressed through the topic-entry type's predicates. The check's **position** in the accept path (after the effective-subscription/registration checks, before signature verification — 013 FR-015) and its **outcome** for every case MUST be unchanged; this is a behaviour-preserving refactor of expression only.
- **FR-008**: The registered-topics projection in `NodeState` and the `TopicRegistryEvent` fold MUST carry the topic-entry type (or fold cleanly into it), keeping the per-topic publisher data encapsulated. The fold MUST be **defensive** (amending 013's lenient fold, Clarifications 2026-06-15): only a `Registered` event creates a topic in the projection; a `PublishersChanged` for a topic not currently registered MUST be dropped and logged (cause: topic not registered) rather than auto-creating it (no `or_default` create); a `Removed` for an unknown topic is a no-op. `Registered` (create/replace), `PublishersChanged` on a registered topic (apply add/remove diff), and `Removed` on a registered topic (delete + cascade, FR-002) otherwise behave as in 013. The 013 fold test that asserted `or_default` auto-creation MUST be reworked. (Delivery note: this FR has two clauses landing in different stories — the **defensive fold** is realised with the invariant work in US1; **carrying the `TopicEntry` type** is the US2 refactor. Both are behaviour-equivalent to a bare set plus the defensive checks.)

#### Scope boundaries

- **FR-009**: This feature MUST NOT merge the topic registry and the subscription list into a single registry or a single merged event: they remain two distinct artifacts (013 / 008) with distinct traits and readers; consistency is achieved by the maintained invariant + cascade over the two separate streams, per the team premise.
- **FR-010** (flipped — 004 merged, Session 2026-06-17): the connection-state cascade IS in scope. A topic-registry `Removed` MUST cascade into the `upstream` and `downstream` structures (drop every connection entry on the removed topic) within the same atomic fold (FR-002). The S7 / N-015 cross-registry gap is **resolved**: under strict drop an unregistered topic is never in the subscription/candidate sets, so a connection `Request` on it fails membership validation and is **rejected** (acceptance is consistent with registration). This feature MUST update `IMPLEMENTATION_NOTES` N-015 / the S7 staleness row to record the resolution. (The 004 acceptance-path *code* is otherwise unchanged — strict drop makes the unregistered-topic case unreachable rather than adding a new check there.)
- **FR-011**: This feature MUST NOT introduce topic-registry governance (owners/admins/RBAC/replication/retention/soft-delete) into the node-consumed projection beyond making the topic-entry type *ready* to carry such fields; the projection stays registered-topics + authorized-publishers (013 FR-017). No new write surface beyond what 013 provides.

#### Testing discipline

- **FR-012**: The invariant, strict drop, and cascade MUST be verifiable as a **pure** state-machine exercise (scripted `Vec<Event>` mixing `TopicRegistryUpdate` and `MembershipUpdate` through `apply`; assert both `subscriptions ⊆ registered_topics.keys()` **and** `candidates.keys() ⊆ registered_topics.keys()` after every step; assert a self-membership event for an unregistered topic leaves the subscription set unchanged — strict drop, no auto-promotion; assert a candidate event for an unregistered topic is not recorded — candidate gating; assert a `PublishersChanged` for an unknown topic does not create it — defensive registry fold; assert the `Removed` cascade clears the subscription set, candidates, and the projection together; assert every `apply` returns an empty `Vec<Effect>`). The topic-entry type MUST be unit-tested in isolation (openness + authorization predicates). The behaviour-preservation of the receive path MUST be asserted against the 013 accept/drop matrix. The cross-stream readiness gate (FR-005) MUST be covered so that a cold-start multi-node bring-up converges deterministically (no spurious drop). Tests MUST assert on state/snapshots/events — **never** on log content (Constitution). Pre-existing 013 tests that assumed the read-time-intersection model or the lenient (`or_default`) fold MUST be reworked, and the 013 success criterion the resolution removes (**013 SC-004**, subscribe-before-register) MUST be updated/removed in lockstep, with its test replaced by the strict-drop + readiness coverage.

### Key Entities

- **Consistency invariant** (`subscriptions ⊆ registered_topics.keys()` **and** `candidates.keys() ⊆ registered_topics.keys()`): the maintained property of `NodeState` this feature elevates from a read-time intersection (013) to an always-true state invariant over both membership-derived structures; the precondition 004's acceptance/dialing logic will rely on.
- **Defensive folds** ("validate, don't assume", uniform across all three folds): self-subscriptions, candidates, and the topic-registry projection each reject inputs that would violate the invariant — strict drop for membership topics that aren't registered, and create-only-on-`Registered` for the projection (a `PublishersChanged` for an unknown topic is dropped, not auto-created).
- **Cascade-on-delete**: the fold behaviour for `Removed { topic }` — drop the topic from subscriptions, candidates, and the registered-topics projection atomically within the single `apply` fold, leaving no per-topic residue.
- **TopicEntry** (new): the declarative per-topic registry entry wrapping the authorized-publisher set; exposes openness + publisher-authorization predicates; the extension point for future governance fields. Replaces the bare `BTreeSet<PublicKey>` at call sites and the inline open-topic check.
- **Registered-topics projection** (reshaped): `NodeState`'s topic → `TopicEntry` map, folded from the topic-registry stream; the right-hand side of the invariant.
- **Subscription set** (single, maintained): the node's accept-filter, now a single `NodeState` set that always satisfies the invariant — no separate declared/pending buffer. A membership event for an unregistered topic is dropped, not buffered. Returned directly by the single subscriptions getter (no read-time intersection).
- **Strict drop**: the enforcement rule — a self-membership event naming an unregistered topic does not enter the subscription set and is logged; no auto-promotion on later registration.
- **Topic-registry readiness gate**: the minimal cross-stream ordering this feature adds — the node warms `registered_topics` before folding membership, so strict drop is correct at cold start in the mock. The mechanism (construction-time snapshot seed, or a cold-start "ready" marker) is a plan decision; production gets this ordering from the chain follower.
- **Ordering premise + node enforcement** (chain-order): the chain/indexer publishes the two registries' events in order (topic registered before any subscription referencing it; deletions in order) — the *source* of consistency. The node does not assume this; it **enforces** the invariant by dropping violating events and surfacing a log, robust against the mock's unordered watches and defensive against a real indexer/ordering fault.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: After **every** fold step, both the node's stored subscription set and its candidate-map topics are a subset of its registered-topics set (the maintained invariant), verifiable by a pure state-machine test that asserts both subset relations after each event — including events that name unregistered topics (strict-dropped, leaving the relations intact).
- **SC-002**: When a subscribed topic is removed from the topic registry, the node's subscription set and candidate map contain **no** entry for that topic immediately after the fold (cascade completeness) — not merely filtered at read time.
- **SC-003**: After a topic removal, no node-state structure retains any per-topic entry keyed on the removed topic (no inconsistent intermediate state).
- **SC-004**: The accept/drop outcome for the full 013 matrix (open topic, restricted topic, authorized publisher, unauthorized publisher, unsubscribed topic, unregistered topic, valid/invalid signature) is identical before and after the declarative-`TopicEntry` refactor (behaviour preservation).
- **SC-005**: The open-topic and publisher-authorization decisions in the receive path are expressed through the topic-entry type's predicates, with no remaining inline emptiness-or-membership check on a bare publisher set at the call site (verifiable by inspection / unit coverage of the predicates).
- **SC-006**: The topic registry and subscription list remain two distinct artifacts with no shared trait and no merged event; the node still consumes them through the two separate `Event` variants (no architectural merge).
- **SC-007**: `IMPLEMENTATION_NOTES` N-015 / staleness row S7 is updated to record that the cross-registry chain-order invariant is established here and to state what the 004 rebase must carry through (connection-state cascade + acceptance-path enforcement).
- **SC-008**: A self-membership event naming an unregistered topic does not add that topic to the subscription set, a candidate event naming an unregistered topic does not record the candidate, and a later `Registered` for that topic does **not** retroactively add either (strict drop, no auto-promotion) — verifiable by a pure test.
- **SC-010**: A `PublishersChanged` for a topic with no prior `Registered` does not create the topic in the registered-topics projection (defensive fold) — verifiable by a pure test; only `Registered` creates a topic.
- **SC-011** (cascade incl. connections): after a topic `Removed`, no `upstream` or `downstream` entry keyed on that topic remains (the cascade extends to connection state) — verifiable by a pure test.
- **SC-012** (event-driven establishment): a node dials its expected upstreams once synced (the registry indexer folds both registry snapshots, then pushes `Event::Synced`, which transitions the node to `Synced` and establishes connections), with no setup timer configured — verifiable by a multi-node integration test reaching `Active` autonomously, and by `Node::is_synced()` flipping. A connection `Request` on an unregistered topic is rejected (S7 resolved).
- **SC-009**: A cold-start bring-up of one or more nodes against pre-populated topic and subscription registries converges deterministically to each node's correct subscription set (registered ∩ its subscription-list topics) with no spurious drop from a cross-stream race — verifiable by the reworked multi-node test passing without timing flakiness (the readiness gate, FR-005).

## Assumptions

- **Feature 013 has merged** (PR #55, on `main`): the `TopicRegistry`/`InMemoryTopicRegistry`, `TopicRegistryEvent`, `Event::TopicRegistryUpdate` + `handle_topic_registry_update`, the `registered_topics` projection, the collapsed single `subscriptions()` getter (effective accept-filter), and the authorized-publisher accept-path all exist. This feature extends that `NodeState`/`apply` core (004 event-loop refactor, ADR 0011/0012; 008 membership fold, ADR 0013/0014).
- **Chain-order premise + node-side enforcement by dropping** (resolved with the maintainers, Clarifications 2026-06-15). On-chain contracts enforce that a subscription can only reference a registered topic, and the chain follower delivers the two registries' events to the node queue in chain order (registration before subscription; deletions in order) — the *source* of consistency. The node does **not** assume it: it maintains a single `subscriptions ⊆ registered` set and **drops** events that would violate the invariant, logging them. The node-side **topic-registry readiness gate** (FR-005) supplies, for the mock's two unordered watches, the cross-stream ordering the chain follower provides in production.
- **Two registries stay separate** (team decision): no merge into a single indexer-level registry and no single merged delete event; consistency is the maintained invariant + cascade + readiness gate over two separate streams. (Re-examined and explicitly declined.)
- **013 SC-004 is superseded.** The subscribe-before-register dynamic 013 guaranteed is intentionally removed by strict drop; its test is reworked into strict-drop + readiness coverage (FR-012).
- **Connection scope** (~~deferred~~ — **superseded by the 2026-06-17 rebase; now in scope**, see Clarifications 2026-06-17). Originally, with 004 unmerged, the connection-state cascade and acceptance-path resolution were deferred. After 004 merged and 014 rebased onto it, the `upstream`/`downstream` fields exist: the `Removed` cascade now clears them (FR-002/FR-010) and S7/N-015 is resolved (an unregistered topic is never subscribed/candidate, so a `Request` on it is rejected).
- **Behaviour preservation for the steady state.** For topics that are registered and stay registered, message acceptance is byte-identical to the merged 013 (008/003) behaviour; the observable changes are the eager atomic cascade on removal and strict drop of subscriptions to unregistered topics.
- **`TopicEntry` is publishers-only for now**, matching 013's node-facing projection; it is *shaped* to carry owners/admins later (011/012) but carries none here (team decision: exclude metadata fields). Identity stays `PublicKey`; the `PeerId`/`PublicKey` unification remains N-009 (011).
- **Reused**: the 013 topic-registry stream + fold, the 008 membership stream + fold, the 003 signature-verification accept path, the 004 pure-core `apply`/`Effect` discipline, and the event-queue seam (`specs/event-loop-and-registry-contract.md`).
