# 0034 — Model-family seams: unified link selection, cell-structured store, fan-out as the dissemination-model knob

**Status**: Accepted (feature 015; amends 0033 — the M3 trigger of its §2 is **superseded**; builds on 0032)

**Context**: Denis's executable dissemination models landed on `main` (`formal_spec/hybrid_dissemination/models/`, M1–M5), and the workstream goal is to support **M3, M4, and M5** as experiment configurations of one node. The authoritative M3 description (`m3/README.md`) settles two things ADR 0033 had left to an interpreted trigger: **"each node opens s−1 standing initiation links"** — unconditionally, not gated on missing relay downstream — and **"initiation links carry only their owner's own publications — they are never part of the relay graph."** M4 (`m4/README.md`) is one bidirectional RF pick-set flooding all incident links, no seeding; M5 (`m5/README.md`) is directed k_in pull picks + k_out outbound picks where **both** kinds carry every held message and there is no seeding semantics. The models differ in (a) which link classes exist, (b) which classes a message travels on — not in the handshake mechanics. Separately, maintaining per-role strategy *types* (`HashGatedConnection` vs `HashGatedPublish`, `ConnectionStrategy` vs `PublishStrategy`) duplicated a ~15-line selection loop and made every future model variant a new type family.

## Decision

1. **The M3 trigger is removed; initiation links are always established.** `Publisher`/Out links (the model's s−1 initiation links; `publish_degree` ≈ s−1) are selected unconditionally on every dial tick, exactly like relay picks. The 0033 §2 trigger ("only when no expected relay downstream") is superseded — it was an interpretation the published model text contradicts.
2. **One link-selection seam, role-parameterised.** A single `LinkSelectionStrategy::expected_links(&NodeView)` trait serves both slots (`relay_selection`, `publish_selection` on `NodeState`); the concrete family is `none` | `connect-to-all` | `hash-gated` (`HashGatedSelection { role, self_id, degree, bucket_override }` — the union of the former `HashGatedConnection`/`HashGatedPublish`, drawing from the role's hash domain). The acceptance side follows the same shape: one `AcceptanceParams { role, degree, … }` per slot, `for_role` on the policies, no per-role kind family. `none` on the relay slot is an accept-only node (the passive-amplifier shape of the golden-node anchor).
3. **The link store is cell-structured.** `LinkStore { relay_out, relay_in, publish_out, publish_in }` (one ordered `LinkCell` each) replaces the quad-keyed map, so a strategy reads **exactly the fields its model prescribes** — and unions them where the model says so — instead of filtering a shared map. `NodeView.links: &LinkStore`; role-scoped acceptance counting is `LinkStore::inbound_scan`.
4. **Fan-out is the dissemination-model knob.** `FanoutStrategyKind`: **`forward-to-all`** (default — relay-in for every message ∪ active publish-out for a local origin; behaviour-preserving, and the reading under which a publisher also serves its own message to its requesters, cf. M3's "a forwarder relays every message it holds") and **`role-scoped`** (the strict M3 partition — local publications over initiation links *only*, relayed traffic over relay links *only*; a node running it without a publish slot is a **mute publisher**, documented on the type). The M4 incident-flood and the M5 no-distinction union are follow-on kinds (M4 additionally needs the symmetric establishment of feature 016; M5 additionally needs the receive-side publisher binding of 0033 §5 relaxed — both noted, not built here).
5. **Both M3 fan-out readings stay available deliberately.** The model text supports the union reading at the origin node (the publisher is a forwarder and "relays every message it holds"), while the strict partition matches "never part of the relay graph" taken as a per-link exclusivity. The experiments cross-validate each against the model's coverage laws; configuration, not code, arbitrates.

## Consequences

- Model sweeps are pure configuration: M3 ≈ `hash-gated`/`hash-gated` selections + `role-scoped` (or `forward-to-all`) fan-out; M4/M5 arrive as one fan-out kind (+ 016's symmetric predicate / a gate relaxation) each, with no new seam shapes.
- One strategy family per seam: adding a selection policy automatically offers it to both roles; the duplicated loop and the parallel kind enums are gone (`edge::hash_gated_selection` remains the shared core).
- Defaults unchanged end to end (`connect-to-all` / `accept-from-all` ×2 / `none` / `forward-to-all`): relay-only behaviour is byte-identical (015 SC-001).
- The wire, the store keying, and the role-dispatched acceptance of ADR 0032/0033 are unchanged; 0033's publisher-binding receive gate stays in force for M3 configurations.

## Alternatives rejected

- **Keeping the trigger as a strategy variant** — no model in the published family uses it; carrying an unconsumed policy contradicts the forward-compatible-interfaces standard.
- **Per-model node modes** (`--model m3|m4|m5`) — collapses the strategy space the experiments exist to sweep; the meeting's three-questions decomposition wants the axes independent.
- **A single keyed map with filter helpers** — workable (it shipped first) but every strategy pays a full-store scan and the cell a policy reads is implicit; the cell struct makes the model's link classes first-class fields, which is what the M4/M5 union strategies select over.
- **Renaming `LinkRole::Publisher` for M5's everything-carrying k_out links** — deferred: the role names the *link class*; what a class carries is the fan-out/gate policy's business, and M5 lands later with its own feature.
